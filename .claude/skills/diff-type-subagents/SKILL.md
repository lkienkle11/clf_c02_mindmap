# Diff-Type Subagents

The orchestrator is the agent session that runs this skill, whatever its vendor. It coordinates, writes task briefs, talks to the user and reviews every task and the whole branch. Workers are the agents recorded in the models table and verified at Gate 1: CLI agents, and a subagent of the host's own mechanism if the host has one. Never assume that any CLI or model is available. This skill never replaces or weakens the approval gates of the workflow in use (spec, plan, branch, commit, merge, push). Settings that depend on the machine or the user (which agent orchestrates, which models are forbidden, effort ceiling, fallback order, quota thresholds, command prefix, handoff folder) are not written in these rules; they live in `policy.md`.

**Announce:** "I'm using the diff-type-subagents skill."

## How to use

Type one of these. The skill keeps its settings for you; you never edit a file to configure it.

| Typed | Meaning | What happens |
|---|---|---|
| `/diff-type-subagents` | Use the current configuration | If the config is missing or incomplete, run `setup` first. Otherwise check the marker (see Where the config lives), then Gate 1A (a models table with no verified row goes to intake question 1 and Gate 1B). |
| `/diff-type-subagents setup` | Configure this machine | If a complete config already exists, `setup` is the same as `reset` (the old config is moved to a backup first, after the user confirms). Ask the user to confirm creating the config folder, then create it from `references/templates/`. Probe the `Environment` table, ask for each policy item that has no default (except the fallback order and the equivalents, which are asked after the CLIs are verified, at Gate 1B step 5), ask which CLIs are installed (intake question 1) and, for each, question 2 (the Hello test and probes, with the remember option), run Gate 1B for them, probe the skill roots. Every write shows its diff first and waits for the user's confirmation. `setup` writes the marker last, after everything else of `setup` (the `Environment` table, the CLIs, the skill roots) is confirmed. Once `setup` has verified the CLIs, continue with the task, do not ask again which CLIs exist, and do not repeat the Gate 1A re-check for them in this session. |
| `/diff-type-subagents reset` | Start the configuration again | If any topic of the handoff root has a `pending` or `running` run, or a recorded workspace entry that is not settled (see Workspaces, merge and wrap-up), stop, name it to the user and say they can wait for it, stop it themselves (a process is never stopped without the user's agreement) or settle the entry with a decision of their own; move nothing. Otherwise tell the user that the config is shared by every project on this machine (a run in another project would lose it) and ask them to confirm, move the config folder to `~/.claude/diff-type-subagents.bak-<YYYY-MM-DD-HHMM>/` (never delete it; if that name exists, add a numeric suffix), then run `setup`, which asks everything again and never reads the backup. |
| `/diff-type-subagents target: a, b` | Use only these CLIs as workers for this run | A hard filter, per run. It is not stored in the config; it is written to the `Intake` section of the topic, so that a resumed topic keeps it. If the config is missing or incomplete, run `setup` first. A named CLI that already has verified rows in the models table goes to Gate 1A (re-check, no new Hello test); a named CLI with no verified row goes to Gate 1B (what is verified is recorded in the models table as usual). The typed list is the answer to intake question 1, so that question is not asked. When `host` is listed, Gate 1A's host-row check runs for the host. If no named CLI passes and `host` is not listed, stop and ask the user. Every other CLI in the table is ignored for this run: escalation chains and fallback entries use only the named CLIs, and when a step leaves no row the rule of `references/allocation.md` applies (stop and ask the user, who may widen the list). The host's own subagent mechanism is in the pool only when the list contains the word `host` (for example `target: host, opencode`). A name that matches no installed program is reported and never guessed. An empty list asks the user which CLIs to use (the word `host` may be named). A name given twice counts once. |

The older free-text form `/diff-type-subagents I installed: <CLI one>, <CLI two>` keeps working: it says these CLIs exist and is not a filter (a CLI with verified rows goes to Gate 1A, any other to Gate 1B).

## Where the config lives

The skill holds rules and blank templates only. Everything recorded on a machine lives in one per-user config folder, the same whatever vendor orchestrates: `~/.claude/diff-type-subagents/`, with two files of settings (backup copies `<file>.prev-<date>` may sit beside them):

- `policy.md`: machine and user settings (orchestrator, forbidden models, effort ceiling, fallback order, equivalents, quota thresholds, spread, completion signal, parallel limit, liveness window, command prefix, handoff root), the `Environment` table, the tier map, the skill source roots and the `Standing consents` table.
- `models.md`: the models table, worker capabilities, the command shapes, pre-flight checks, session-list rows and quota notes of each CLI as verified on this machine.

In these rules "the policy" means `policy.md` of the config folder, and "the models table" (with Worker capabilities, Pre-flight check commands and the Session-list table) means `models.md` of the config folder. `references/models-and-commands.md` is the procedure file only: the rules for keeping and writing the models table, the capability and eligibility rules and the command-shape rules live there, and the recorded rows live in `models.md`. The blank starting files are in `references/templates/`. Items that depend on the host (`Orchestrator`, `Completion signal`) hold the value of the host that last ran Gate 1; a different host re-probes them.

**Missing or incomplete config.** If the folder is missing, holds only one of the two files, or has a `policy.md` whose marker is still the template placeholder (`<hostname>`, an interrupted setup), treat it as no config: run `setup`, never use a half config and never offer the marker question for it. A folder in one of the last two states is first moved to a `.bak-` folder exactly as `reset` does, after the user confirms the move (never overwritten, never deleted), and its answers are asked again. If the folder cannot be created or written (for example `$HOME` is unset or not writable), report it to the user and stop; never write the config anywhere else. After the user has confirmed creating the folder, check that it can be written before any probe, using an empty temporary file that is not config and is removed at once. A complete config that is read-only is a read-only config: use it for reading, tell the user once that the skill cannot record anything new, and when a write would be needed show its diff and ask the user to fix the permissions or continue without recording.

**Every write to either file** (setup, a change of `Completion signal`, a new table row, the marker update, a consent) shows its diff first and waits for the user's confirmation; the empty temporary file of the writability check is the only exception. Before the first change to an existing config file in a session, keep its previous text as `<file>.prev-<YYYY-MM-DD>` in the config folder (one per day, never overwritten; a backup copy needs no confirmation). The config folder is not a git repository, so there is nothing to commit and no history to read.

**The marker.** The first line under the title of `policy.md` is `Configured for: <hostname> | <operating system and shell> | <date>`. Every session, before Gate 1, compare it with the live machine. The operating system and the shell are the hard keys; the date is never compared. On a mismatch or a missing marker, change nothing and ask the user once: (a) reconfigure for this machine (same as `reset`), (b) keep the config and update the marker, (c) cancel. If only the hostname differs (a hostname that depends on the network), ask the same question once; answer (b) updates the marker, so the question does not repeat. The `Environment` comparison of Gate 1 stays as a second guard.

## When this skill applies

**Trigger.** The user types `/diff-type-subagents`, or asks to delegate work to other agents or CLIs. A request in words counts as the command typed with no list, or, when it names CLIs, as the `I installed:` form with those CLIs (never a filter, and a CLI with verified rows goes to Gate 1A, any other to Gate 1B). Setup and the Gate 1 checks may run at any earlier time and need no task list.

- **Moment of effect.** The skill takes effect at the earliest moment a decision it governs, who does a piece of work, is about to be taken, and not earlier. Before that moment it stays out of the way: it does not delegate, and it asks nothing except the part 1 questions of the intake, which are asked when the command is typed.
- **With a workflow.** The skill is an overlay: it never replaces the workflow in use and never weakens that workflow's approval gates. Each step of the workflow is a Gate 3 point from the moment of effect on; before it, the Gate 3 answer is silent and leads to Gate 2 only for a step the user asked to delegate. The natural moment is when the workflow's tasks are about to be executed (for example, when the user chooses how to execute an approved plan, delegating is one more way to do it). It takes effect earlier only when the user asks to delegate earlier work such as research or reconnaissance. The skill does not describe the internal steps of any other workflow; it names only the moment.
- **With no workflow.** A request to delegate is a one-step workflow: intake, table, approval, run, review.
- **Typed late.** The skill takes effect from the current step on. It reads the files already on disk (spec, plan, ledger, `assignments.md`) and never asks again what they answer.

## Questions and standing consents

### The intake

One list of questions, shown once per topic, and only for questions whose answer is not already known from the config, the standing consents, the typed command or the files of the topic. Part 1 is asked when the command is typed, after the config and marker checks and before the Gate 1 probes it covers (in `setup`, questions 1 and 2 are the questions `setup` itself asks about CLIs and probes; they are not asked twice). Part 2 is asked after the read-only analysis of Gate 2 steps 3a to 3g (ripple scan, ripple classes, skill resolution, groups, allocation) and before the table of step 4 is shown; this is the point that Gate 2 step 5 calls asking before the table. Each question has a default, and the reply "accept the defaults" answers every question of the part except questions 2, 6b and 6c, which are always answered in words: a default is never permission to run a worker, spend quota, create a workspace folder, a task worktree or a branch, or choose where workers write. "Accept the defaults" never stores a consent. Where a question is marked, the answer may be "yes and remember", which stores a standing consent. As soon as the topic has a name (taken from the plan or the user's request), the skill creates the topic folder (see Ownership and names) and a draft `assignments.md` (`Status: draft`) so that the answers have a place; these are the skill's own records under the handoff root, not project files, and until then the answers are kept in the conversation and written when the folder is created; answers that are not stored are written to its `Intake` section: a topic resumed in a new session, or an older topic with no `Intake` section, asks only what is unanswered and reads the rest from the file.

| # | Part | Question | Default | Can be remembered |
|---|---|---|---|---|
| 1 | 1 | Which CLIs to use (asked only when no list was typed and the models table has no verified row at all; with verified rows the config is trusted, and the user adds a CLI by typing `I installed:` or `target:`) | the CLIs the user names | no |
| 2 | 1 | Run the Hello test and the capability probes for each CLI that needs them. The question says what the probes do: every probe run spends quota, the write check writes one file in a probe folder under the handoff root, the read check reads one file outside the working folder, the web check opens one documentation page. It also covers the one-time host-probe question of Gate 1A | none: always asked in words | yes |
| 3 | 1 | Delegate from the start, or only at execution (asked only when the command was typed at the first step of a workflow) | only at execution | no |
| 4 | 2 | An independent reviewer for the final review (row "R" of `assignments.md`; a yes adds row R, chosen by allocation step 3 of `references/allocation.md`, after this question) | yes | yes (a "yes" or a "no") |
| 5 | 2 | The four ripple classes of Gate 2 step 3b | the four classes | yes (the kinds only; the files and the regenerate command stay per task in the table) |

The answer is written to the `Intake` section in the user's words with the date; a workspace that the table did not cover when it was given (added by a split or a later change) needs the question again | none: always asked in words; nothing is created until yes | no (the project requires permission each time) |
| 6c | 2 | Only if no workflow gave a base: use the branch checked out in the user's folder as the base, or ask the user to check out another one (the skill never checks out or switches a branch; if that branch is the repository's default branch, another must be checked out unless the user explicitly agrees to use it) | none: always asked in words | no |

If question 3 is answered "from the start", the work to delegate first (research, reconnaissance) is the task list of a first table, built and approved as usual, and later tasks are added by Gate 2 step 6. If it is answered "only at execution", the answer is recorded and Gate 3 sends the orchestrator to Gate 2 when the workflow reaches execution.

### Standing consents

- A standing consent is a row of the `## Standing consents` table of the user's `policy.md` (`Consent | Covers | Granted | Scope`). Its scope is always this machine. A missing section, or no row, means no consent.
- A row is written only when the user answered "yes and remember" (or "no and remember" for question 4) in words, through the usual diff and confirmation. If the section is missing, the same diff adds the heading and the table header. A row names its CLIs and their versions in the `Covers` cell (the word `host` may be named); storing a consent for another CLI adds that CLI to that row, in the same diff.
- A row covers exactly what it says: question 2 covers the Hello test and capability probes, and the host-probe question, for the CLIs named in the row at the versions named; a CLI that is not named, or whose version changed, is asked about. Question 4 covers the choice of reviewer; a stored "no" gives way when Gate 6 step 1a makes the independent reviewer mandatory (the host has no review mechanism of its own), and the user is told. Question 5 covers the four classes by name.
- A consent only removes a question. It never skips a check: the Gate 1A re-check of a CLI (login, live model list) still runs.
- "No" at the intake for a CLI that is in a row applies to this run only, is recorded in the `Intake` section of `assignments.md`, and leaves the row in place. The user withdraws a consent by saying "forget <consent>"; the removal shows its diff first. `reset` moves the config, so every consent is gone after it.

### Never stored

These are asked every time, whatever consents exist: anything irreversible or touching real data; a write outside the folders that the approved table names or outside the allowed paths; a merge other than a task branch into its workspace branch (question 6b), a push or a publish; any change of worker, model, effort, mode, write permission, scope, delivery mode or skill hash after approval (except a move along the approved chain); a violation found at Gate 5; a failed or stopped run when the approved chain has no slot left (a move along the chain is told, not asked); quota exhausted at the end of the chain; a conflict, a cycle or a missing skill; and the approval of the table itself (Gate 2 step 4).

## Workspaces, merge and wrap-up

Used when intake question 6b is answered yes. With 6b "no", nothing below is created: the write tasks run in order in the base the workflow gave (writes happen only in a branch the user allowed, and if that branch is the repository's default branch the user is asked first; the approval of the table, which names the working folder, is that permission), read-only tasks follow `references/parallel-groups.md` (edge (f) puts them after the writers), and the orchestrator makes no commits: the skill tells the user that the changes stay uncommitted in the working tree until the user commits them, each run's Gate 5 baseline includes the earlier runs' changes, and the final review reads the working-tree diff. With 6b "yes" and 6a "no", all tasks form one workspace, run in order, with no task worktrees. With both "yes", the full model below applies.

### Terms

Three words, each with one meaning in this skill. Read them first.

| Word | Meaning | On the machine |
|---|---|---|
| **base** | the place the workflow in use works in (the branch or worktree it created with the user's permission), or, with no workflow, the user's current branch. This skill never creates it and never removes it | the user's own branch or worktree |
| **workspace** | a set of tasks tied together by shared files or dependencies; tasks in different workspaces cannot touch each other. Named `w1`, `w2`, ... With 6a "no", all tasks form one workspace. A task that only reads and has no edge is not a workspace: it runs in a detached copy of the base branch | one git worktree (a folder) with its own branch, made by this skill from the base |
| **task worktree** | the own folder of one task that runs at the same time as another task of the same workspace | one more git worktree with its own branch, made by this skill from the workspace branch |

The repository's default branch is the one that `git symbolic-ref --short refs/remotes/origin/HEAD` names (without `origin/`), or `main` or `master` when there is no remote; when in doubt, ask the user. A workspace is a set of tasks first and a worktree second: the skill says "workspace" for the set and for its folder and branch together. The Gate 4 task folder (`brief.md`, ledger) is a different thing: it holds records, not code.

### Ownership and names

- The workflow in use owns the **base**. This skill owns only the workspace folders, task worktrees and branches it creates, and records every one of them. The topic's own branches are `diff-agents/<topic-folder>/*`; the base is not one of them.
- `<topic-folder>` is the whole name `YYYY-MM-DD-<topic>` of the topic folder under the handoff root (Gate 4); `<topic>` is a short name (lowercase letters, digits and hyphens only; never `probe` or `worktrees`, which are folders of the handoff root) taken from the plan or from the user's request. Before the first write under the handoff root, check `git check-ignore` for it; if it is not ignored, stop and tell the user (adding the line to `.gitignore` is the user's decision). If a topic folder with unsettled entries already exists, ask the user whether the work is that topic or a new one.
- A **workspace** is a connected part of the conflict graph (`references/parallel-groups.md`, Workspaces and folders). Workspace folder `<handoff-root>/worktrees/<topic-folder>/<workspace>/`, branch `diff-agents/<topic-folder>/<workspace>`, made from the base. A **task worktree** (not the Gate 4 task folder, which holds `brief.md` and the ledger) is never inside a workspace folder: `<handoff-root>/worktrees/<topic-folder>/<workspace>--<task-id>/`, branch `diff-agents/<topic-folder>/<workspace>--<task-id>`, made from the workspace branch. No branch name nests inside another (git cannot hold `a/b` and `a/b/c` together). Workspaces are named `w1`, `w2`, ... in the plan order of their first task, and task ids are the plan's; the `parallel group` column holds `<workspace>.G<n>` (for example `w1.G1`). The handoff root is ignored by git, and these folders stay clear of the `.worktrees/` and `worktrees/` places that the workflow's own clean-up looks at in the project root.
- Create each folder with `git worktree add -b <branch> <path> <start-point>` (a read-only detached copy, path `<handoff-root>/worktrees/<topic-folder>/<workspace>--ro-<task-id>/`, cut from the workspace branch, or from the base branch when the task has no workspace: `git worktree add --detach <path> <branch>`; the start point of every other folder is its parent branch name; to retry an interrupted add on a branch that already exists, `git worktree add <path> <branch>` is allowed) and nothing else: never `-B`, `-f` or `--force`. Run every git command of this skill as `git -C <recorded path>` after checking that `git -C <path> rev-parse --show-toplevel` is that path and `git -C <path> branch --show-current` is the recorded branch (a detached copy has no branch); a mismatch stops and asks. Before removing anything, check that the path lies under `<handoff-root>/worktrees/<topic-folder>/` and, unless it is a detached copy, that the branch starts with `diff-agents/<topic-folder>/`; otherwise report it and do nothing. The base is the first entry of the `Workspaces` section (path and branch, never removable) and is the target of the git commands that act on it.
- A skill copy of the `workspace-copy` delivery mode goes to `<the worker's working folder>/.diff-agents/skills/<skill name>/` (a task worktree or the workspace folder; with 6b "no" nothing is written into the user's base and the mode falls through to `compiled`), so that the mode stays valid. The orchestrator first writes `.diff-agents/.gitignore` containing `*`, so that git ignores the whole folder: it is never committed, never shows as untracked and does not make a folder "not clean".
- Workers never run a git command (WORKER RULES): the orchestrator creates, commits, merges and removes.

### States

Every folder and branch is an entry in the `Workspaces` section of `assignments.md` (path, branch, parent, state, and the folder decision of each round). The entry is written as `planned` when the table is approved, before anything is created, so no folder exists without an entry. States: `planned`, `created`, `committed` (the work is committed on its own branch), `merging` (written before a merge starts, so that a lost context knows it was attempted), `merged` (merged into its parent: a task into its workspace, a workspace into the base), `stopped (<reason>)`, `kept (user decision)`, `cleaned`. An entry is settled when it is `kept (user decision)` or `cleaned`. A read-only run's detached copy is an entry too, with the same states, and is offered at wrap-up like the other folders. Write a state after the git action is verified, never before (only `planned` and `merging` are written first). A new orchestrator session resumes from these states: first reconcile with git: `git worktree list`, `git branch --list 'diff-agents/<topic-folder>/*'`, the `git status` of each workspace folder and `git branch --merged`. A `planned` entry whose folder exists and is registered in `git worktree list` on the recorded branch becomes `created` (a folder that exists but is not so registered is reported and never touched); a folder or branch under the topic's names that has no entry is reported to the user and never touched; an interrupted `git worktree add` leaves a `planned` entry that is retried or settled with the user's word. A merge found in progress is never aborted by the skill (see Merge). An entry found in `merging` with no merge in progress means a merge was started and aborted or interrupted: the skill does not retry it, it tells the user and asks to resolve or abandon. `stopped` applies to a workspace entry and to the entries of its task worktrees; when the user resolves it, they return to the state they had before the stop and are not yet settled.

### Merge

- **Precondition.** Before a workspace is cut, the base is clean (no modified and no untracked file) and everything the workers need is committed; if not, stop and ask the user to commit or stash. The same check is made before the first write when 6b is "no", so that a worker never writes over the user's own uncommitted edits. Inputs that are not committed (briefs, results, skills) are read by absolute path, as briefs already do.
- **Order for a round**, for each run (a task that ran in the workspace folder has no task branch: it counts as merged once it is committed on the workspace branch): the Gate 5 check against its own baseline; then the review (Gate 6 step 1; here "run the verification commands yourself" means the light checks, and the heavy ones run after the merge); then the orchestrator commits that folder's changes to that folder's branch (a round that ran in the workspace folder commits to the workspace branch, before any task worktree of the next round is cut): it stages only files inside the run's allowed paths (never `git add -A`), writes the message that the project's commit rules require (its Reviewed and Tested lines state what was really done), and never uses `--no-verify`; then the task branches are merged into the workspace branch in table order, from inside the workspace folder, with `git merge --no-ff -m <title> -m <body>`, a message that follows the project's commit rules (four sections, no AI attribution or co-author trailer); then the heavy checks (the project's build or full test, the commands named in the table and approved with it) run once in the workspace folder (after the merge, or after the commit when the round had no merge); then a task of the next round is cut from the updated workspace branch once every task it depends on is merged (or committed on the workspace branch); a failed task holds back only the tasks that depend on it. Before the first worker runs in a new worktree, dependencies must be there: the table names a setup command for each workspace (empty means none), the user approves it with the table, and the skill runs only that command, once per new worktree, in it; if workers need dependencies and there is none, the workspace stops before any launch.
- Use real merge commits only (no squash, no rebase), so that `git branch -d` works and no force flag is needed.
- **Checks.** In a task worktree run only the light checks the task's brief names, on the task's own files. The project's build and full tests run only in the workspace folder after the merge. The skill installs nothing: if the dependencies are missing there, the heavy check reports it, stops that workspace and tells the user which command is needed; the user installs them or says what to do.
- **A failed run in a round.** The branches of runs that passed Gate 5 and review merge as above. A run that violated Gate 5 is handled by Gate 5 (stop and ask the user); a run that failed for another reason stays in its task worktree and goes through Gate 6 step 2 (a successor continues there). A fix after the final review (Gate 6 step 1a) runs in a task worktree cut from the workspace branch (in the workspace folder when it runs alone), is merged the same way, and wrap-up waits until it is.
- **A conflict or a failed check.** A merge conflict, or a failed check after a merge, stops that workspace (state `stopped (<reason>)`), tells the user and changes nothing else; other workspaces continue. After a conflict the orchestrator aborts the merge it has just started (`git merge --abort`, in the same step, so that the folder is clean and nothing of the user's is lost), records the two branch names, and asks the user to resolve it or to abandon that workspace. To resolve, the user merges the two branches by hand in the workspace folder and says so; the orchestrator then checks that the task branch is an ancestor of the workspace branch (`git merge-base --is-ancestor`) and that the workspace folder is clean, and continues. A conflict while merging a workspace branch into the base is handled the same way, in the base folder: the merge is aborted there, the user merges by hand in their own folder and says so, and the orchestrator checks that the workspace branch is an ancestor of the base. If the heavy checks fail after a merge into the base, report it; the skill never resets or reverts the user's branch. Write `merging` before each merge. A merge found in progress when a session resumes is never aborted by the skill: it asks the user. A stopped workspace is never merged into the base until the user decides. A `stopped` entry leaves that state when the user decides: resolved (back to its earlier state, the workspace continues) or abandoned (the entry becomes `kept (user decision)`). If the context is lost between the abort and the `stopped` entry, the new session finds the entry unchanged and the two branches unmerged: it asks the user instead of retrying the merge.
- **What question 6b covers.** Creating the folders and branches, the orchestrator's commits in them, the detached copies of read-only runs, and merging task branches into their workspace branches. Merging a workspace branch into the base is not covered: it is asked at wrap-up, after the final review. A merge into the repository's default branch is never done by this skill (the user does it) and never stored.

### Wrap-up

When every task of every workspace is merged into its workspace branch (or its workspace is settled, see Merge) and the final review (Gate 6 step 1a) is recorded, ask the user the first question, carry it out if the answer is yes, and then ask the second. For the final review the whole branch means the diffs of all workspace branches against the base. The default of each is no. (1) Merge the workspace branches into the base now? List each workspace branch. This is offered only when the base is not the repository's default branch, the base folder is clean and idle, and its current branch is still the recorded base; the merge is a real merge commit, and a conflict stops as described in Merge. After the merge, run the project's heavy checks once in the base folder and report the result. (2) Remove the folders and branches this skill created? List each with its state (merged and clean, or not). A failed, paused or violating run keeps its folder. Never offer anything that holds unmerged work or uncommitted changes (report it only), never touch the base or anything the workflow created, and only entries of the `Workspaces` section are eligible. Remove task worktrees first, then delete their task branches (`git branch -d`, run in the workspace folder, whose HEAD contains them), then remove the workspace folder; a detached copy is removed with its workspace. Remove a folder with `git worktree remove` from outside the folder, never with `--force` (git removes a folder that holds only ignored files, such as build output, without it); a folder with any modified or untracked, non-ignored file is "not clean". Delete a workspace branch with `git branch -d` run in the base folder, only after its folder is gone and it is merged into that HEAD; a branch that is not merged is kept and reported. Never use `-D`. Once the user has answered, every entry that was kept or only reported settles as `kept (user decision)`, and removed ones become `cleaned`.

### Reset guard

`reset` stops when any topic of the handoff root (when there is no config yet, `.superpowers/diff-agents/` of the current project) has a pending or running run, or an entry that is not settled (a `stopped` entry blocks until the user settles it, see Merge). A user decision settles entries without wrap-up: when the user abandons the topic, its entries become `kept (user decision)`, and a `planned` entry whose folder was never created is settled as `cleaned`.

## Hard rules

- A model, a model family or an effort level that `policy.md` forbids is never used as a worker. The orchestrator's own model family is a worker only if the policy allows it.
- A worker never reviews its own output. Whoever writes a change does not approve it. A worker's "verified" or "done" is never evidence.
- Never use a flag that bypasses approvals or the sandbox (the flags of each CLI are listed in `models.md`). For any CLI not listed there, never a flag whose documentation says it skips permissions, approvals or the sandbox. Never use an effort level above the policy's effort ceiling unless the user asks.
- Read-only unless the user explicitly allowed writes for this task. Writes happen only inside an isolated worktree or branch that the user allowed. The one exception is the probe runs (the Gate 1B Hello test and capability probes, and the Gate 1A host probe), covered by the user's consent: no probe run writes outside its probe folder, except the scratch file of check (b) that the orchestrator creates under the operating system's temporary folder and deletes after the probe (the rule of Gate 1B step 3b).
- **Every worker session must be listed.** For every worker of any vendor and every task (implement or read-only, finished or running), the session must appear in full in the session list of that worker's own CLI when the user runs that CLI's resume command, including sessions that CLI hides by default (non-interactive sessions, sessions started in another directory). The user must be able to pick a session from that list and see what the worker is doing, in real time while it runs. The exact list command for each CLI is recorded in the models table; a CLI whose list command is not recorded and verified is not used. A list command is verified when it runs and lists a worker session started from the same working folder; listing sessions of other folders and following a live session are shown to the user at Gate 2 as [Unverified] and never silently assumed. The first sentence of this rule is the goal; the test is this one, and the unverified remainder is an accepted relaxation shown to the user, not a block. A row of the host's own subagent mechanism counts as listed only after the user's one-time confirmation (Gate 1A; `references/allocation.md` step 2).
- Workers do not see the project rule files or the host's skills of any agent. This holds for workers of the same vendor as the orchestrator and for workers of any other vendor. Everything a worker needs is in its `brief.md`: so the skills that apply to a task are delivered in its brief by their mode, and the orchestrator checks the proof (Gate 4 step 2a, Gate 5).
- Worker results are leads until the orchestrator verifies them. Sources must be official documentation; blogs and study sites are leads only.

## The gates (do them in this order; do not skip because the task "looks small")

### Gate 1: Which CLIs exist on this machine (once per session, before any assignment)

First run the config check of "Where the config lives" (missing or incomplete config starts `setup`; the marker is compared with the live machine). Then: the models table (`models.md`) is the record of the CLIs and models that were discovered and verified on a machine. Never assume that any named CLI is installed. Choose the path by what the user typed and by whether the table has rows:

- **Flag with no list, and the table has rows:** trust the table, then re-check it against the live CLIs: Gate 1A.
- **Flag with no list, and the config or the table is missing or empty** (a missing or incomplete config folder always starts `setup` first, see How to use): ask the user which CLIs are installed on this machine (intake question 1). Then run Gate 1B for every CLI the user names. The table is created from what is discovered.
- **Flag with a list** (example: `/diff-type-subagents I installed: <CLI one>, <CLI two>`): a CLI on the list that has verified rows goes to Gate 1A (re-check), any other to Gate 1B.

If `policy.md` has no "Skill source roots" section or the section has no verified row (blank cells of the `Environment` table count as missing too), first run the skill-folder probe (Gate 1B step 7) on the orchestrator itself, read-only, and ask the user to confirm the roots before anything is written; the per-CLI probe in Gate 1B then covers each worker CLI.

The orchestrator self-probe also asks, in EVERY session and for the identity of the orchestrator that runs now (not only when the roots section is missing): "can I start a background process and be woken in this session when it ends?" A host that has not been probed counts as `polling`: `native` was verified only for the host of the design session. Record the result in `policy.md` as the item `Completion signal` (`native` or `polling`) with the date and the host identity (`references/running-workers.md`, Completion signal). A value recorded for a different host is ignored: that host counts as `polling`.

**Environment probe.** In EVERY session, once `policy.md` has been read (next paragraph; the `Environment` table lives there), compare the operating-system-and-shell cell of the `Environment` table with the actual one; on a mismatch, or when the user says the setup changed, re-probe (show the diff; the user confirms; if they want to configure everything again, that is `reset`). If the SHA-256 tool or the real-path tool is missing, report it to the user and stop skill resolution (Gate 2 step 3d); never invent a method. On the first run on a machine, when the `Environment` table of `policy.md` is missing, or when the user says the setup changed, probe each item of that table read-only (hostname by the `hostname` command or the platform's equivalent, operating system and shell, tool for the SHA-256 of a file, tool for a real path, how to close standard input, how to start a background process, terminal multiplexer yes or no, scripting runtime for parsing JSON yes or no, how to wait a short interval, how to read the current time). Show the user the diff, and write the table only after the user confirms. Never install anything: a missing tool is reported to the user, who decides. Any tool that gives the same result may be used and is recorded in the table with its date.

Read `policy.md` first, then do the Environment comparison above. If it is missing, run `setup`; if the user says the setup changed, offer the re-probe above, or `reset` if they want to configure again. Nothing in these rules overrides the policy, and nothing in the policy overrides the hard rules above. Compare the policy's "Orchestrator" item with the agent session that is actually running this skill; if they differ, ask the user which is right, and update the policy (diff first).

### Gate 1A: Re-check the CLIs recorded in the table

Run these checks for the CLIs that the table names (read-only; no user question except the one-time host-probe question of the sub-step below, which a stored consent for the host removes). When the user typed a list after the flag, that list is the answer to intake question 1 (a CLI with verified rows goes to Gate 1A, any other to Gate 1B), so the question is not asked twice. For each CLI use the checks recorded for it in the models table and in its `Pre-flight check commands` section (`models.md`); a CLI with no recorded check is treated as unverified (Gate 1B).

1. Login check. A CLI named in the table that is missing, or not logged in, on this machine is reported to the user and is not used. If the CLI has no login-status command, a successful query is the evidence, and say that this is an inference.
2. Live model list. Compare it with the models table (`models.md`) and update the table if they differ (the rules for keeping and writing the table are in `references/models-and-commands.md`, "Keeping the table current" and "How to write into the table"). Parse a long machine-readable list; never print it whole.
3. Effort must be valid for the model, as recorded in the models table (for example, some models have a fixed effort and reject an effort flag).
4. Run in the intended working directory, not a temp directory, when the user wants to see the session later (this includes the Hello test and the session check).
5. Quota read: read the quota percentage if a way exists (record in the table whether one was found).
6. Session-list command: check that the one recorded for each CLI in the table still works (it runs and lists sessions). A CLI whose recorded list command no longer works is reported to the user and is not used. If the command needs an interactive terminal and the `Environment` table says no multiplexer, ask the user to look and confirm, and record it as user-confirmed with the date, in the Session-list table row of that CLI or of the host mechanism; a user confirmation that the new session appears in the list counts as the listing check of the "verified" definition (hard rule on sessions).

Gate 1A does not ask whether another CLI should be added: with verified rows the config is trusted, and the user adds a CLI by typing `I installed:` or `target:` (intake question 1 covers a table with no verified row). Do not offer a menu of workers built from the table's families alone. Report the result in one short block. A subagent of the host's own mechanism needs no CLI check, but it must be a row in the table with its cells probed (the sub-step below) and its session list confirmed once. Its row counts as session-list verified once the user has confirmed, one time, how the host shows the runs of its subagents; record the confirmation and the way to see them, with the date, in the Session-list table (`models.md`). Until then such rows are not chosen.

**Probe the host mechanism per model (Gate 1A sub-step, after the session-list confirmation).** If a host row's cells are missing or `[Unverified]`, or its model is not in the host's live model list, ask the user one question (the purpose is to confirm what a subagent of the host mechanism can do; it will run read-only checks and one write check) and then run the host probe under rule (4) of the probe location rule in Gate 1B step 3b, for each model the tier map names for it, and record the cells in the capability table (diff first). Eligibility is per needed column: a host row is eligible for a task whose needed columns are all `yes`; it is not rejected as a whole because another column is not `yes`.

### Gate 1B: Any other CLI the user listed

Used when the user adds a list to the flag (example: `/diff-type-subagents I installed: <CLI one>, <CLI two>`), or when the table was missing or empty and the user named the installed CLIs. Do not reuse the models table for a CLI on the list that has no verified row. Treat each such CLI as unverified and go through these steps in order, per CLI:

1. **Check auth.** Find that CLI's own way to show login status. If it has none, use a successful query (for example listing its models) as the evidence, and say that this is an inference. Do not assume it is logged in.
2. **Ask the user whether to spawn a "Hello" test task** (intake question 2; skip the question for a CLI named in a stored consent, whose Gate 1A re-check still runs), and state the purpose in the question: to confirm that the CLI is logged in, that its non-interactive command works, and that the session is saved and visible in that CLI's `/resume`. Say also that the test includes six small capability checks (step 3b), one of which writes one throwaway file in the probe folder (only for modes that can write), plus the token files the orchestrator creates in the probe folder, and that the orchestrator deletes the throwaway files afterwards (the token files stay with the probe folder, which is git-ignored). Do not spawn the test before the user agrees. If the user declines, do not use that CLI as a subagent until it has been verified, unless the user explicitly says to skip verification.
3. **If the user agrees, run the test.** Run an interactive session with the working folder as cwd (rule (1) of step 3b), in the safest mode (read-only, no dangerous or bypass flags), send `Hello`, and exit cleanly. Use a terminal multiplexer for this only if the `Environment` table of `policy.md` says one exists; otherwise use the CLI's non-interactive command for the test, or ask the user to run the interactive session in their own terminal and report what they see. Never install a multiplexer. Give the user the exact input, the exact output and the session ID, so the user can compare them with what that CLI's `/resume` shows. Wait for the user to confirm that the session is visible and matches (recorded as user-confirmed with the date, in the Session-list table row of that CLI; this counts as the listing check of the "verified" definition). Also find, from the CLI's own help or official documentation, the exact command that lists every worker session of that CLI, including non-interactive sessions and sessions started in another directory, and test it. Check whether a session that is still running can be opened and followed in real time.
3b. **Probe the capabilities (covered by the consent in step 2).** Probe runs (the Hello test, the capability probes, and the Gate 1A host probe) are an explicit exception to "nothing is delegated before approval", covered by the user's consent (step 2 here; the question of the Gate 1A sub-step for the host).
   **The probe location rule (written here once; the other places point to it).**
   (1) The Hello test and the session-list check always run with the project working folder as cwd, in the safest mode the CLI offers (read-only when it has one), and never write.
   (2) Capability checks of a mode that cannot write by design (a read-only mode): all of (a) to (e) run with the working folder as cwd; the token file of (a) is created by the orchestrator in the probe folder, which lies inside the working folder (the handoff root is a git-ignored folder inside it), and the worker is told its absolute path; the file of (b) stays under the operating system's temporary folder.
   (3) Capability checks of a mode that can write by design (accept-edits style, workspace-write style) and of a CLI that has no read-only mode: ALL of its checks (a) to (f) run with cwd = the probe folder `<handoff-root>/probe/<cli>-<mode>/` (git-ignored scratch created by the orchestrator), whose only permitted write path is that folder; the Hello test and the session check stay as in (1). If the CLI has no read-only mode, say so and ask the user before testing; never use a bypass flag; if the user refuses, the cells of that mode stay `[Unverified]`.
   (4) The host mechanism: (a) to (e) by a read-only host worker, (f) by a write-capable host worker in `<handoff-root>/probe/host-<model>/`, each told its folder in the prompt (a host worker's cwd cannot be set; the limit is by instruction and the baseline detects a violation).
   (5) The probe baseline, defined once: the orchestrator records (i) `git status --porcelain` and the head hash of the project working tree, and (ii) a RECURSIVE listing (path, size, modification time) of the whole handoff root, BEFORE any probe folder or token file is created; it records both again after the last probe run and after the orchestrator deleted the check-(f) files. The handoff root and the `probe/` folder themselves (their own modification times) are excluded. "Zero change" means: git status and head identical, and the listing differs only under a probe folder of this run (any of them: one run may have a folder per CLI and mode). Writes to a git-ignored path outside the handoff root are not seen (known limit).
   Send five tiny read-only prompts and one write check, one per column of the `Worker capabilities (per CLI and mode)` table (they run once per non-bypass mode the CLI offers; a mode not run keeps `[Unverified]` in every cell of its row): (a) = `Reads path`: read a file by absolute path inside its cwd that holds a known token; (b) = `Reads outside folder`: read a file by absolute path OUTSIDE its cwd, a scratch file created for the probe under the operating system's temporary folder (never in a tracked folder), holding a different token, and deleted after the probe; (c) = `Runs commands`: run a harmless command that prints a fixed string (and, if the tasks need tests, a no-op test command); (d) = `Web`: the orchestrator first opens an official documentation page of the CLI's own vendor and notes its exact title, then asks the worker for that page's title; (e) = `Sees skills itself`: ask the worker to list the skills it can see, and where from; (f) = `Writes files`: ask the worker to create ONE throwaway file in the probe folder and read it back (no existing file is touched); the orchestrator deletes it afterwards and, if deleting fails, tells the user the path.
   Pass rules: (a) and (b) are `yes` only if the reply is exactly the known token of that file; (f) is `yes` only if the file exists with the expected content when the orchestrator reads it, and the orchestrator then deletes it; (c) is `yes` only if the reply is exactly the fixed string the command printed; (d) is `yes` only if the worker's title matches exactly; (e) is `yes` if the worker lists at least one skill or rule file with its folder and the orchestrator confirms that file exists, `no` if it replies that it sees none, and `[Unverified]` if the answer cannot be matched to an existing file. Anything else is `[Unverified]`; a cell is `no` only when the reply clearly shows the action is not possible. Each cell carries the check date and names the sandbox or permission mode used for the check, because a read-only mode can block an action that the CLI can do in another mode. A check that was not run stays `[Unverified]` and is never assumed.
   **Eligibility.** A task needs a column when its brief requires that action (a file by absolute path, a file outside the working folder, a command such as a test run, a web page, a skill the worker must find itself, or to create or edit a file in its own folder or allowed paths: column `Writes files`). The orchestrator lists the needed columns for each task in `assignments.md` and checks them against the table at Gate 2. A worker whose cell is `no` or `[Unverified]` in a needed column is not eligible for that task. The six cells are recorded at step 6, in the `Worker capabilities (per CLI and mode)` table.
4. **After the user confirms, list that CLI's models and effort levels** from the CLI's own commands or official documentation: the models, the minimum and maximum effort, which models have a fixed or non-adjustable effort, and whether quota or usage can be read. Say which facts are verified and which are not.
5. **Only then may that CLI's agents be used as subagents.** Add a new CLI to the fallback order in the policy and to a task's assignment only by the user's decision: propose a place for it and ask, never invent its position. Also ask the tier of each new row of the tier map (Small, Medium, Heavy or Very heavy; the default is Small) and the fallback order and equivalents that involve it, and record the answers in `policy.md` after a diff.
6. **Record what was discovered. This step is mandatory.** Before the CLI's agents are used for real work, add a row for every discovered model to the models table in `models.md` of the config folder (the rules for keeping and writing it are in `references/models-and-commands.md`) (vendor and CLI version, model id, effort levels, notes such as "effort fixed" or "not adjustable"), record the CLI's session-list command and whether a running session can be followed in real time, and update the commands, pre-flight checks and quota notes if this CLI differs from the CLIs already in the table. Also add one row per CLI and mode, with the six cells and the check date, to the `Worker capabilities (per CLI and mode)` table in the same file. Mark anything not verified as **[Unverified]**, and write the date. Tell the user which rows were added. Do not leave discovered models only in the conversation. Show the user the diff before writing it as final (the config folder is not a git repository, so there is nothing to commit).
7. **Probe the skill folders (read-only; also run for the orchestrator itself).** Find where this agent looks for skills and whether it scans a folder by itself: its documentation, its help, the folders that exist on this machine. Change nothing. Show the findings to the user; write them to the "Skill source roots" section of `policy.md` (with the date, and [Unverified] for what was not tested) only after the user confirms. For the orchestrator, ask the host first, then the user.

A subagent of the host's own mechanism, and the orchestrator rules, do not depend on any CLI; the host row still needs its cells probed and its session list confirmed once (Gate 1A).

### Gate 2: Delegation plan and approval (before the first delegation, and whenever anything changes)

1. Before the first delegation, create (or complete, if part 1 already created it) `<handoff-root>/YYYY-MM-DD-<topic>/assignments.md`. The file starts with two lines, `Status: draft` and `Next step: <the next action; the questions waiting for the user>`. Step 4 and step 6 change the first line; the orchestrator rewrites the second after every launch, result, question and answer, and writes every allocation decision and every user decision to a file when it is made. A table with no `Status` line is `draft`: add the line. Besides the main table, the file holds the sections `Intake` (the answers of the intake that were not stored as consents; a resumed topic reads them from here), `Skill resolution`, `Delivery table`, `Parallel groups`, `Workspaces` (path, branch, parent, state and the folder decision of each round) and `Allocation record`. Under the two lines, one row per task (the mark `(write-mode row for a read-only task)`, `references/allocation.md` step 2, is shown in the `why` cell for the row's own mark; the chain slots carry theirs in the `escalation chain` column): `work item | worker | model | effort | mode | read-only or write | allowed paths (plan files + ripple list) | ripple classes | CLI verified | skills the worker must read | why | needed capability columns | escalation chain | time limit | parallel group`. The `escalation chain` column names the next rows in advance; the choice and the chains are also written to the section `Allocation record` of `assignments.md` (`references/allocation.md`). `<handoff-root>` is the handoff folder from `policy.md`; it must be ignored by git. For each task, "skills the worker must read" lists every skill that applies to that task: the skills the user selected for the workflow step this task belongs to (a selection file of a workflow is optional input: when the user keeps one, use it; without one, the orchestrator's own judgment of what applies decides), plus any other skill the orchestrator judges relevant to the code or files the task touches (for example a language or framework skill, a testing skill, a UI skill). Write "none" only when no skill applies, and say why. The user can add or remove skills when confirming the table. The table always ends with a row "R" for the final whole-branch review (Gate 6 step 1a): it says which review mechanism the orchestrator will use, and asks the user whether to add an independent read-only reviewer worker (with its model, effort and the review skill it must read).
2. Assign only a CLI and model that passed Gate 1A or Gate 1B and appear in the models table. A subagent of the host's own mechanism needs no CLI check but must be a row in the table with its cells probed, and is chosen only after the user has confirmed how the host shows its subagent runs (Gate 1A). Show the user, per chosen row, what is [Unverified] about its session list (other folders, following a live run).
3. Choose workers by `references/allocation.md` (steps 0 to 8): weigh each task, filter the rows, rank by tier only (never by price), spread equal choices as the policy says, write the choice and the escalation chain into the `Allocation record`. A row with no recorded result for a kind of task may be chosen as a pilot, with a closer review. If a step leaves no row, stop and ask the user; never downgrade silently.
3a. **Ripple scan (before the table is shown).** For every task that writes, find what its change will break elsewhere BEFORE the allowed paths are fixed. Use read-only means only (search, the compiler or type checker's view, the project's schema and contract tools, reading the guard checks). The orchestrator performs the scan itself, read-only; it is never delegated before approval. List, per task:
   - **Consumers** of whatever the task changes: code that calls, imports, queries or builds it (a type, a function, a table or column, an endpoint, a message or event, a config key, a public contract), plus generated artifacts derived from it (clients, ORM models, schema files, API docs).
   - **Tests, fixtures and seed or sample data** whose assertions or values describe the behavior the task changes on purpose.
   - **Guard checks** that cover the touched area (type check, lint, architecture or boundary rules, schema or migration validation, contract tests, translation key checks) and what they require.
   - **Ordering and compatibility:** whether the change makes a check red, or breaks a running consumer, between this task and a later one (a new required field, a removed export or column, a migration that a deployed version does not yet understand). Reorder the tasks, or split the change in compatible steps, so every commit stays green and, where it matters, every step is safe to deploy.
   The result is the task's ripple list. Allowed paths = the files the plan names + the ripple list.
3b. **Pre-approved ripple classes (the table lists them per task; with a stored consent they are shown as already accepted, otherwise intake question 5 asks; the approval of the table still confirms them).** A class is a kind of mechanical edit a worker may make without stopping, only in files of the ripple list:
   - propagate a change to the places the compiler, type checker or schema validator flags (for example a new field or parameter, a renamed column in queries);
   - update an existing test or fixture so it asserts the behavior this task changes on purpose (never delete, skip or weaken it);
   - regenerate a generated artifact with the project's own command;
   - satisfy a guard rule the project already enforces (public entry point, declared key list, naming).
   The brief's "Allowed paths" section names each class and the exact files it covers, so WORKER RULES item 2 stays word for word true. The worker reports these edits under a heading "Ripple edits", and the orchestrator reviews them like any other change. An edit outside the classes, or in a file that is not in the list, is a stop (WORKER RULES item 2 applies unchanged).
3b-bis. **Never a ripple class; always a stop and a question to the user:** anything irreversible or destructive or touching real data (dropping or rewriting data, editing a migration that has already shipped or run, a data backfill, changing a contract consumed outside the repository, deleting a resource, touching production or a user's live database). For these the orchestrator also shows the plan first and asks for a backup or a dry run before anything is carried out.
3c. A small correction of the same task may resume the same worker session instead of opening a new one.
3d. **Resolve skills.** For each skill name in "skills the worker must read", follow `references/skill-delivery.md` section 1: walk the roots of `policy.md` in order, take the real path, compute the combined hash, and write one row into the section `Skill resolution` of `assignments.md` (`skill | real path | root | combined hash | covered files | note`). A conflict, a missing skill, a broken link, a missing linked file or a policy without roots is a stop: ask the user, never guess. If the machine has no SHA-256 tool or no real-path tool (see the `Environment` table of `policy.md`), report it to the user and stop skill resolution; never invent a method.
3e. **Choose delivery modes.** The delivery mode is evaluated per CANDIDATE row inside allocation step 2 (`references/allocation.md`): a row needs at least one working mode for every skill of the task. Follow `references/skill-delivery.md` section 2: take the first mode that the row's capability cells allow (`path`, `workspace-copy`, `compiled`, `orchestrator-keeps`). The final `Delivery table` of `assignments.md` (`worker | skill | mode | proof | confidence`; `worker` is the worker with its mode: CLI, model, mode; proof and confidence from section 3) is written after the row is chosen. At approval it lists a row for every (worker, skill) of the chosen rows AND of every row of their escalation chains (a chain row already passes allocation step 2, so a working mode exists for each skill). If no mode works for any row, stop and ask the user: change the worker, or allow the work without that skill.
3f. **Parallel groups.** Evaluate the whole task list for which tasks may run at the same time, by `references/parallel-groups.md`: conflict edges (the file is the unit), groups `G1`, `G2` and so on, the split evaluation (a split is only proposed, never applied silently), the `Parallel limit` of `policy.md`. Write the `parallel group` column and the section `Parallel groups` of `assignments.md`. Parallelism does not depend on the vendor. Order of Gate 2 step 3 and its sub-steps: the ripple scan (3a), the ripple classes (3b), the skill resolution (3d), the parallel groups, provisional, and any split (3f), then the allocation of step 3 run task by task in plan order (the delivery mode of 3e is evaluated per candidate row inside its step 2), then the re-evaluation of the groups (3g), then the `Delivery table` (3e) for the chosen rows and their chain rows, then the table (step 4). After the groups, derive the workspaces and the folder decision of each round (`references/parallel-groups.md`, Workspaces and folders).
3g. **Re-evaluate the groups (after allocation).** With the pilot edges and the queued tasks now known (`references/parallel-groups.md`, Orientation), re-evaluate the groups. If the split recommendation changes, the split stays a PROPOSAL shown to the user as unallocated; a split part that the user accepts is allocated through steps 0 to 8 of `references/allocation.md` after that acceptance, and the main allocation is not redone. An accepted split part gets its allocation (steps 0 to 8), its chain and its Delivery rows, and the table is shown again for approval (`Status` goes back to draft, step 6). A change of the groups, or an answer at step 5 that changes an edge, recomputes the workspaces and the `Workspaces` section.
4. Show the table, with the `Delivery table`, the `Parallel groups` section and the `Workspaces` section, to the user and **stop until the user confirms all of them**. Confirming the table also confirms the ripple lists and the ripple classes in it. Only then change the first line to `Status: approved`, together with a dated line that quotes the user's confirmation (this is also what Gate 3 requires before any delegation). A summary, a ledger or a remark that the user "seemed fine" never makes a table approved. With `Status: draft`, or with no status line, nothing is delegated. A run launched before approval is a violation: tell the user, keep its result only as a lead (in `notes.md`, under the heading "Leads (run before approval)"), and show the table again for confirmation.
5. Ask part 2 of the intake (questions 4 to 6c, see Questions and standing consents) and the working-folder questions BEFORE showing the table of step 4 for approval, after the analysis of steps 3a to 3g; if the answer changes a group (edge (f)), re-evaluate the groups before the table is shown. If any worker needs write access, the folder it writes in comes from intake questions 6a to 6c (see Workspaces, merge and wrap-up): never assume, and never create a workspace folder, a task worktree or a branch before 6b is answered yes. Writers that run at the same time each have their own working folder, and a branch alone does not give a second working folder. The working folder of every concurrent run, including the copy of the committed state given to a read-only run, is named in the approval table, in the cell of the column `allowed paths (plan files + ripple list)` of that run's row, as a line `working folder: <path>`.
6. Any change of worker, model, effort, mode or write permission needs re-approval unless it is a slot of the approved chain; the same holds for any change of scope, delivery mode or skill hash (Gate 4 step 2a re-check, the failure rule of `references/skill-delivery.md`). Such a change updates `assignments.md`, sets `Status: draft` at once, and needs the user's approval again before it is carried out. The one exception is a move along the escalation chain the user already approved with the table (every chain row already has its Delivery table rows at approval, so a move along the chain needs no new row and does not reset `Status`): it needs no new approval, but it is told to the user and recorded.
7. Do not delegate just because a task is simple or a worker is available.

### Gate 3: Delegation check before every step of the workflow in use

Before each step of the workflow in use (for example, with Superpowers: brainstorming, research, spec, plan, implementation, verification, review), answer in one line: "Delegable? yes/no, worker or reason". Default is **yes** for research, codebase reconnaissance, builder checks, plan-task code and independent review; **no** for talking to the user, approval gates, git commits, merges and pushes. If the answer is yes and the step has no row in `assignments.md`, go back to Gate 2 and get approval first. Nothing is delegated before approval: delegation needs `Status: approved` in `assignments.md`. The probe runs (Gate 1B and the Gate 1A host probe) are the named exception (consent; the rule of Gate 1B step 3b).

### Gate 4: Brief and handoff (every delegated run)

**Before creating any brief, read `references/worker-rules.md`.**

1. The orchestrator creates the task folder under `<handoff-root>` (from `policy.md`, ignored by git):
   ```
   <handoff-root>/YYYY-MM-DD-<topic>/<task-id>/
   ├── brief.md          goal, scope, allowed paths, output format, stop condition
   ├── ledger.json       one entry per run, marked pending, running, done, or failed, with the agent and model that ran it
   ├── notes.md          sources found, items still unsure, decisions taken
   └── results/
       └── batch-NN.json one result file per batch, written as soon as the batch finishes
   ```
   A RUN is one ledger entry; a BATCH is a result file `results/batch-NN.json` inside a run. A single read-only run needs only `brief.md`, its run entry in `ledger.json` and its log or result; `notes.md` and `results/` are for runs with several batches or for write tasks.
2. `brief.md` starts with the WORKER RULES block from `references/worker-rules.md`, copied word for word, for every worker. For a worker that writes code, the CODE WORKER RULES block follows it, also word for word, then the plan task's own steps (they carry the exact test names, signatures and commands). Then the task, its allowed paths, its output file and its stop condition. For EVERY read-only task the worker never writes the result file: the CLI's output option or the orchestrator saves its final reply; the brief names that result path but the worker does not create it, and WORKER RULES item 5 is read that way (the brief says so after the block: "The result file named in this brief is saved from your final reply by the orchestrator or the CLI's output option; do not create it."). A task with the mark `(write-mode row for a read-only task)` additionally gets in its brief, after the WORKER RULES block, the sentence: "This task is read-only: write nothing at all; any change makes the run invalid." (rule: `references/allocation.md` step 2; `references/worker-rules.md` stays untouched). For a read-only task with no output file, the task part says that the answer is the worker's final reply and that the orchestrator saves it. Never write "follow the project rule file" or "use the skill" in a brief; deliver each skill by its mode as step 2a says. The command prefix of `policy.md` applies to commands the orchestrator runs and reads; it is never part of a command given to a worker or run through the launch wrapper (its output goes to a log file).
2a. **Skills for the worker (every worker, whether of the same vendor as the orchestrator or another).** A worker does not see skills, so for every skill listed for this task in `assignments.md`, deliver it by the mode in the `Delivery table` (`references/skill-delivery.md` sections 2 to 4). Recompute the combined hash of the skill right before the brief is written and stop if it changed (section 1). Name every skill that applies, one entry each; never a name only, and never a summary in place of the path, the copy or the checklist.
   - `path`: the brief names the real path with the sentence of section 2.
   - `workspace-copy`: the brief names the copy's path; it never states the nonce.
   - `compiled`: the checklist of section 4 is in the brief, nonce on its first line.
   - `orchestrator-keeps`: the skill is not in the brief.
   - Record in the table `Worker capabilities (per CLI and mode)` whether the CLI can read a file by path; a nonce is fresh per worker, per skill and per run, and is written to `ledger.json` (section 2).
3. **Where a worker may write:**
   - A code worker may modify the source files listed under the user-approved "Allowed paths", and only those.
   - Reports and results go only to the output path named in the brief. A read-only worker's result goes back to the orchestrator (either the CLI's own option to write its last message to a file, as recorded in the models file, or a redirection of the CLI's output, in both cases into a file inside the task folder).
   - "Inside its own task folder" applies to state and result files (`ledger.json`, `notes.md`, `results/`), which the orchestrator writes. It never blocks a code worker from editing its allowed source paths.
4. **One task, one fresh session.** Do not carry one chat from task A to task B: no anchoring on earlier conclusions, the rules sit at the top of a short context, a short context uses less quota, and each task may use a different model and effort. Reusing a session is allowed only for a retry or a small correction of the same task while the context is still small. The files stay the source of truth.
5. **Keep workers on task:** one output file with a fixed schema; list the paths a worker may read and write, a stop condition, and "do nothing outside this list"; run non-interactive so workers cannot ask questions back (stdin closed, see `references/running-workers.md`); small batches that finish quickly, with results written to disk after every batch; constrain prompts tightly, because some models add follow-up work on their own.
6. Deliverables that the user reviews or that belong in the project (reports, specs, plans) go to the tracked location the task's spec or plan names, built from the `results/` files. A task folder that lies under a path ignored by git (by any `.gitignore` in the project) needs no cleanup: leave it in place and do not ask about it; delete it only if the user asks. If a task folder is NOT ignored by git, tell the user that it is not ignored (so it would show in `git status` and could be committed by mistake), never commit it, and let the user choose: add its path to a `.gitignore`, move it to an ignored path, or delete it.
7. **Launch so that the chat is not blocked.** The command is built from the chosen row's mode (the mode flag of that row in `models.md`) and the ledger entry records the mode; a run started in another mode than the row's is invalid and stops. Start every run as its own process (or the host's background subagent) as described in `references/running-workers.md`: the launch wrapper, a ledger entry with the baseline of the working folder (Gate 5) recorded before the launch call and marked `running` with the launch time right after it returns, the `done` marker, the time limit and the rule for parallel runs. The tasks of one group (`references/parallel-groups.md`) start together, unless the parallel limit forces them to start in parts; write members run in the folders the approved table names, each created from its `planned` entry before launch (state `created`); without question 6b answered yes they run one after another in group order; record each concurrent writer's working folder in its ledger entry; a later group starts when the tasks it depends on are done and reviewed. Never run a worker as a blocking command in the chat. A run is finished only when its `done` marker exists.
8. **Session check after every launch.** Right after starting a worker, run that CLI's session-list command from the models table and confirm that the new session is listed. Give the user the session name or ID and the exact command to open it. If that command needs an interactive terminal and the `Environment` table says no multiplexer, ask the user to look and confirm, and record it as user-confirmed with the date, in the Session-list table row of that CLI or of the host mechanism; a user confirmation that the new session appears in the list counts as the listing check of the "verified" definition (hard rule on sessions). If the command shows a prompt that is not the list (an update offer, a notice), never choose an option that installs or changes anything: dismiss it only with the option that skips it once, and if it cannot be dismissed without installing, ask the user to look and confirm (see Session visibility in `models.md`). If the session is not listed, pause that run (halt your own progress; see Gate 5; do not continue the task with it), tell the user exactly what you saw, stop the process only after the user agrees, and let the user decide what to do (for example another run mode, or another CLI). Do not continue the task with an unlisted session.

### Gate 5: Compliance check after every worker run (mandatory, by the orchestrator)

A run is finished when its `done` marker exists (`references/running-workers.md`). Read `exit.code`: absent or not 0 means the run failed (Gate 6 step 2). Never read a run's result before `done`. The check is made per run against that run's allowed paths. Record its result as `compliance` (`passed` or `failed`) in the run's ledger entry.

BEFORE the launch call the orchestrator records, in the run's ledger entry, a baseline of the working folder the run uses: the `git status --porcelain` output, the head hash, a fingerprint of the tracked changes and the list of untracked files. The result needed: any change since launch is detectable, including a change to a file that was already modified and any untracked file (example only: a hash of `git diff` for the fingerprint, and `git ls-files --others --exclude-standard` for the list). The check compares the run's own working folder with that baseline: the commit count and head hash unchanged, and `git diff --name-only` inside the allowed paths (add the command prefix from the policy, if any). A read-only run must show NO change at all (there is no allowed-path comparison to make). Two runs must not share one working folder if either writes: a read-only run that is active at the same time as a write run has its own working folder (a separate worktree or a copy of the committed state) or, if it cannot, is placed in a later group (edge (f) of `references/parallel-groups.md`). "Stop" and "pause" (here and in Gate 4 step 8) mean that the orchestrator halts its OWN progress on that run and tells the user; a process is only stopped with the user's agreement. The limit-waiter is exempt (the orchestrator stops its own waiter after a normal finish). A paused run keeps status `running`, its limit keeps counting, and the user is told so. On any violation: stop, show the user exactly what happened, undo only what the worker changed outside its allowed paths after the user agrees, and do not treat that run's output as valid. A worker's own statement that it followed the rules is never evidence. For a task with the mark `(write-mode row for a read-only task)` the baseline comparison must show zero change in the working folder (`references/allocation.md` step 2).

**Skill-read check (same gate, every run).** For every skill named in the brief (step 2a), check the proof of its mode (`references/skill-delivery.md` section 3) and give the result its confidence label:
- `path`: the worker's log shows an open event for the skill file (section 3) before the first step of the work. Confidence high. A `path` run whose log cannot show the order of events is not allowed: the mode is `workspace-copy` from Gate 2.
- `workspace-copy`: the nonce line of the copy is quoted in the report. Confidence medium.
- `compiled`: evidence for every step, the nonce quoted, and the orchestrator re-ran the verification commands and they agree. Confidence lower.
- `orchestrator-keeps`: verified by whoever holds the work; the label is that of the holder's own mode.
A result from `workspace-copy` or `compiled` gets a closer review, like a fallback to a weaker model. Failures (each makes the run invalid; stop and tell the user which skill): `path` with no open event: mark `Reads path` [Unverified] in the capability table (show the diff first), take the next mode. `workspace-copy` with a missing nonce: mark `Reads path` [Unverified], take `compiled`. `compiled` with a step lacking evidence, a missing nonce, or a re-run that disagrees: take `orchestrator-keeps`. In every case ask the user to approve the changed `Delivery table` before the run is repeated. If `orchestrator-keeps` cannot be verified by its holder, or no mode works: stop and ask the user (change the worker, or allow the work without that skill). A worker's statement that it followed a skill is never evidence.

### Gate 6: Review, quota, fallback and recovery

1. **Review.** Read the diff, run the verification commands yourself and read their output. For every disputed item and for a sample of "verified" ones, read the newest official page yourself. Review every task and the whole branch. Record the result as `review` in the run's entry of `ledger.json`. After a round's review, its task branches are merged as the Workspaces section says; a stop of one workspace does not stop the others. This reading is the first step of review, never the whole of it: step 1a adds the final review.
1a. **Final review, when every task is done and before the branch is offered for merge (mandatory).** Reading the diff yourself does not replace it. Run both of these, in this order, and record each result in the ledger:
   - **The orchestrator's own review mechanism on the whole branch.** Use the review capability the orchestrator's host provides (for example a code-review skill or command, or a requesting-code-review skill), in a read-only mode (never one that applies fixes or posts comments), at the effort level the user allows and never above the policy's effort ceiling. Choose the effort from the size and risk of the diff being reviewed: **low** for a small mechanical or documentation-only diff; **medium** for a small diff that changes logic; **high** for a large diff, or one that touches scoring, persistence, migrations, security or a public contract. A final whole-branch review is sized by the whole branch, not by the last commit. Record the level and the reason in the ledger. Name which mechanism was used. If the host has none, say so, and the independent reviewer below becomes mandatory.
   - **An independent reviewer when the user wants one (row "R" of `assignments.md`).** A read-only worker, in a fresh session, that is not the session that wrote the code, chosen by `references/allocation.md` (step 3): its family must differ from the family of the writer of the highest-risk task, with the same relaxation and label `low` independence if no such row exists. It follows Gate 4 and Gate 5 like any worker: a brief that starts with WORKER RULES, the review skill or method delivered by its mode (Gate 4 step 2a), with its proof checked (Gate 5), the diff range to review, and a single output. Its findings are leads: verify each one yourself before acting, re-grade by effect, fix Critical and Important findings with a failing test first (through a worker, under Gates 2 to 5), and record Minor findings as deferred.
   Do not tell the user that the work is reviewed until both applicable steps are recorded. If the user chose "orchestrator reviews, no independent reviewer", record that choice and still run the orchestrator's own review mechanism.
1b. **Pilot result.** When a pilot's review passes, the orchestrator writes `(CLI, model, effort, kind): passed <date>` into the notes of the models table (`models.md`; show the diff first). `references/allocation.md` step 5 reads those notes and the ledgers of the current topic.
2. **When a worker stops** (reason `quota`, `error`, `launch` or `wrong-mode`; a timeout is `stuck`) or is stuck (`references/running-workers.md`, Hang detection): read the ledger, check the last "done" batch for truncation, then give the successor the brief, the finished results and the notes with the instruction "continue from the first batch that is not done; do not redo done batches". A batch that was being written when the old agent stopped counts as not done and is redone. The orchestrator does not take the task over itself and does not restart it from zero.
3. **Fallback goes through files.** The new agent never receives the old agent's session. Build a new brief from the files, never by retelling from memory. `notes.md` must record sources found, items still unsure and conventions agreed, because the old agent's private reasoning is lost.
4. **Quota and fallback:** a fallback follows the escalation chain approved in `assignments.md` (`references/allocation.md`); the fallback order, the equivalents and the quota thresholds are in `policy.md`, and never lower a task's tier silently. After the last entry in the fallback order is exhausted: stop, save the ledger, report the state to the user, and do not continue. A result produced after a fallback to a weaker model gets a lower confidence label and a more careful review. For high-value work where accuracy matters, tell the user that waiting for the quota to reset may be better than a weaker model, and let the user choose. Detect running out of quota reactively: a non-zero exit code, a rate-limit or usage-limit message in the output, or HTTP 429. Tell the user each time a fallback happens: which agent, which task, which batch, and why.
5. **When the orchestrator itself stops** (quota, error, closed session): all state is in the task folder (`brief.md`, `ledger.json`, `notes.md`, `results/`) and in `assignments.md` at the topic level (its `Status:` and `Next step:` lines). A new orchestrator session, started by the user with an agent the user chooses, reads those files and the assignments, runs Gate 1, and continues from the first obligation (run, compliance, review) that is not passed. The user decides which agent takes over (a new session started by the user is the user's choice of successor); the orchestrator never appoints its own successor. The new session starts with step 6.
6. **Resume point.** After a context compaction, when a session is reopened, or whenever the orchestrator cannot tell what was decided, it first re-reads `SKILL.md`, `policy.md` and `assignments.md` (and the references the situation needs) before it delegates or reviews anything. It reads `assignments.md` FIRST (the `Status` and `Next step` lines), then every per-task `ledger.json` of the topic, and starts from the first obligation (run, compliance, review) of any run that is not passed; `status: done` means only that the process finished. If `assignments.md` is absent or its `Next step` is stale, ask the user; never assume. Every allocation decision and every user decision is written to a file when it is made, never kept only in the conversation; a decision found only in a summary or in memory is asked again. `assignments.md` is approved only by its `Status: approved` line with the dated quotation (Gate 2 step 4). A run launched before approval is kept only as a lead in `notes.md` under "Leads (run before approval)".

## Red flags

| Thought | Reality |
|---------|---------|
| "I'll just do this one myself, it's quick" | Run Gate 3. The default for delegable work is to delegate. |
| "The task is simple, I'll delegate without the table" | Nothing is delegated before the user approves `assignments.md` (Gate 2). |
| "The user already approved the plan, so the assignment is approved" | Approval of a spec or plan is not approval of the assignment. |
| "I'll switch the model, it's a small change" | Any change of worker, model, effort, write permission or scope needs approval again (Gate 2 step 6). The one exception is a move along the escalation chain approved with the table. |
| "I'll tell the worker to follow the project rule file" | It cannot see it. Read `references/worker-rules.md` and put the blocks in `brief.md`. |
| "The plan steps are enough, the worker doesn't need the skills" | A worker sees no skill. If a skill applies, deliver it by its mode (Gate 4 step 2a) and check its proof (Gate 5). |
| "The skills the user selected for this step are for me, not for the workers" | They apply to whoever does the step's tasks. Put them in the assignments table and in each brief. |
| "A worker of my own vendor surely has the skills too" | Never assume. A same-vendor worker is a fresh session with no skills until its brief names them. |
| "This CLI surely reads files outside its folder" | Never assume a capability. Probe it at Gate 1B (step 3b); an unprobed cell is [Unverified] and the worker is not eligible for a task that needs it. |
| "It cannot read the path, so skip the skill" | Choose the next delivery mode (`workspace-copy`, `compiled`, `orchestrator-keeps`) from the probe. If none works, ask the user; never drop the skill silently (`references/skill-delivery.md` section 2). |
| "It quoted the skill, so it read it" | A worker's statement is never proof. Check the proof of the mode: an open event in the log, or the fresh nonce and per-step evidence (section 3). |
| "I know where this skill lives" | Paths come from the `Skill resolution` table, never from memory or from where a skill was loaded (Gate 2). |
| "The skill is the same in both folders" | Compare the combined hashes. Different hashes are a stop, not "first root wins". |
| "The worker ran fine, its session list doesn't matter" | Every worker session must be listed and checkable by the user. Run the session check (Gate 4, step 8). |
| "I'll write this model or vendor name into the rules" | Machine and user settings live only in `policy.md`. The rules stay vendor-neutral. |
| "The worker said it passed" | Run the command yourself (Gate 6). |
| "I read the whole diff and the tests are green, so the branch is reviewed" | That is step 1 only. Run the final review (Gate 6 step 1a): the host's own review mechanism, and an independent reviewer if the user wants one. |
| "The user chose 'orchestrator reviews', so no review tool is needed" | The choice removes the independent reviewer, not the host's review mechanism. Run it and record it. |
| "Any CLI named in a request is surely installed" | Never assume. Table has rows: re-check it (Gate 1A). No table: ask the user, then discover (Gate 1B). |
| "The table lists this model, no need to check the machine" | Re-check the live CLI against the table every session (Gate 1A). The table lists only what was discovered; the user adds a CLI by typing `I installed:` or `target:`. |
| "This listed CLI is probably logged in" | Unverified until Gate 1B is done. |
| "I found a new model, I'll remember it" | Write it into the models table, or the next session loses it. |
| "I'll just pick the cheapest model" | Rank by tier only, never by price (`references/allocation.md` step 5). Cost is quota, not price per token. |
| "Everything goes to one family, it is simpler" | Apply the Spread setting at step 6 of `references/allocation.md`; if only one family passes step 2, say so to the user. |
| "Task A and task B can share one chat" | One task, one fresh session. State goes through files. |
| "It should be done by now" | Check the `done` marker, then the limit counted from the launch time in the ledger entry. Past the limit with no `done`: Hang detection. |
| "The notification will come, I do not need the marker" | Files are the source of truth. Never report a result before its `done` marker exists; under `polling` check at every pause point. |
| "My summary says the user approved it" | A summary is not approval. Only `Status: approved` with a dated quotation of the user's confirmation in `assignments.md` counts (Gate 2 step 4). |
| "I remember the decision" | After a compaction or in a new session, re-read the files first (Gate 6 step 6). A decision that is not in a file is asked again. |
| "There is no selection file, so no skill applies" | A selection file is optional input. Without one, judge what applies to the task yourself (Gate 2 step 1). |
| "These tasks look independent, I will start them all" | Independence is decided by the conflict edges, with the file as the unit, and by the `Parallel limit` (`references/parallel-groups.md`). Two tasks that edit different parts of one file still conflict. |
| "They are different vendors, so they run one after the other" (or "...so they may overlap") | Parallelism does not depend on the vendor. Only the edges, the group rule and the limit decide, and write tasks at the same time need a worktree the user allowed. |
| "The worker is stuck, I'll finish it myself" | Hand the files to a fallback agent: continue from the first obligation (run, compliance, review) that is not passed; inside a run, from the first batch that is not done. |

## Reference files

- `policy.md` of the config folder (`~/.claude/diff-type-subagents/`; see Where the config lives): machine and user settings (orchestrator, forbidden models, effort ceiling, fallback order, equivalents, quota thresholds, command prefix, handoff folder), the `Environment` table, the tier map and the skill source roots. Created by `setup` from `references/templates/policy.md`. Read at Gate 1.
- `models.md` of the config folder, and `references/models-and-commands.md`: the first is this machine's record (models table, worker capabilities, command shapes, pre-flight checks, session-list rows, quota notes), created from `references/templates/models.md`; the second holds the generic procedure for keeping it current.
- `references/templates/`: the blank `policy.md` and `models.md` that `setup` copies. `README.md`: a short guide for people (the commands, where the config lives, how to reset).
- `references/allocation.md`: how to weigh a task and choose its worker (steps 0 to 8), the roles and families, the escalation chain and the `Allocation record` table. Read at Gate 2 step 3.
- `references/skill-delivery.md`: how a skill name is resolved to a real path and a combined hash (section 1), how it is delivered to a worker by mode (section 2), how reading is proved (section 3) and the compiled checklist format (section 4).
- `references/running-workers.md`: how a worker runs as its own process: the launch wrapper, the `done` completion marker, the completion signal (`native` or `polling`), hang detection and the time limit, and parallel runs. Read at Gate 4.
- `references/parallel-groups.md`: how a task list is evaluated for parallel groups: inputs, conflict edges, the group rule, the split evaluation, limits and the record in `assignments.md`. Read at Gate 2 step 3f.
- `references/worker-rules.md`: the WORKER RULES and CODE WORKER RULES blocks, to copy word for word into briefs.
