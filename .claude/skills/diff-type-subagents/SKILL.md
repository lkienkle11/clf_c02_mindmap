# Diff-Type Subagents

The orchestrator is the agent session that runs this skill, whatever its vendor. It coordinates, writes task briefs, talks to the user and reviews every task and the whole branch. Workers are the agents recorded in the models table and verified at Gate 1: CLI agents, and a subagent of the host's own mechanism if the host has one. Never assume that any CLI or model is available. This skill never replaces or weakens the approval gates of the workflow in use (spec, plan, branch, commit, merge, push). Settings that depend on the machine or the user (which agent orchestrates, which models are forbidden, effort ceiling, fallback order, quota thresholds, command prefix, handoff folder) are not written in these rules; they live in `references/policy.md`.

**Announce:** "I'm using the diff-type-subagents skill."

## Hard rules

- A model, a model family or an effort level that `references/policy.md` forbids is never used as a worker. The orchestrator's own model family is a worker only if the policy allows it.
- A worker never reviews its own output. Whoever writes a change does not approve it. A worker's "verified" or "done" is never evidence.
- Never use a flag that bypasses approvals or the sandbox (the flags of each CLI are listed in `references/models-and-commands.md`). For any CLI not listed there, never a flag whose documentation says it skips permissions, approvals or the sandbox. Never use an effort level above the policy's effort ceiling unless the user asks.
- Read-only unless the user explicitly allowed writes for this task. Writes happen only inside an isolated worktree or branch that the user allowed.
- **Every worker session must be listed.** For every worker of any vendor and every task (implement or read-only, finished or running), the session must appear in full in the session list of that worker's own CLI when the user runs that CLI's resume command, including sessions that CLI hides by default (non-interactive sessions, sessions started in another directory). The user must be able to pick a session from that list and see what the worker is doing, in real time while it runs. The exact list command for each CLI is recorded in the models table; a CLI whose list command is not recorded and verified is not used. A list command is verified when it runs and lists a worker session started from the same working folder; listing sessions of other folders and following a live session are shown to the user at Gate 2 as [Unverified] and never silently assumed. A row of the host's own subagent mechanism counts as listed only after the user's one-time confirmation (Gate 1A; `references/allocation.md` step 2).
- Workers do not see the project rule files or the host's skills of any agent. This holds for workers of the same vendor as the orchestrator and for workers of any other vendor. Everything a worker needs is in its `brief.md`: so the skills that apply to a task are delivered in its brief by their mode, and the orchestrator checks the proof (Gate 4 step 2a, Gate 5).
- Worker results are leads until the orchestrator verifies them. Sources must be official documentation; blogs and study sites are leads only.

## The gates (do them in this order; do not skip because the task "looks small")

### Gate 1: Which CLIs exist on this machine (once per session, before any assignment)

The models table in `references/models-and-commands.md` is the record of the CLIs and models that were discovered and verified on a machine. Never assume that any named CLI is installed. Choose the path by what the user typed and by whether the table has rows:

- **Flag with no list, and the table has rows:** trust the table, then re-check it against the live CLIs: Gate 1A.
- **Flag with no list, and the table is missing or empty:** ask the user which CLIs are installed on this machine. Then run Gate 1B for every CLI the user names. The table is created from what is discovered.
- **Flag with a list** (example: `/diff-type-subagents I installed: <CLI one>, <CLI two>`): run Gate 1B for every CLI on the list.

If `references/policy.md` has no "Skill source roots" section, first run the skill-folder probe (Gate 1B step 7) on the orchestrator itself, read-only, and ask the user to confirm the roots before anything is written; the per-CLI probe in Gate 1B then covers each worker CLI.

The orchestrator self-probe also asks, in EVERY session and for the identity of the orchestrator that runs now (not only when the roots section is missing): "can I start a background process and be woken in this session when it ends?" A host that has not been probed counts as `polling`: `native` was verified only for the host of the design session. Record the result in `references/policy.md` as the item `Completion signal` (`native` or `polling`) with the date and the host identity (`references/running-workers.md`, Completion signal). A value recorded for a different host is ignored: that host counts as `polling`.

**Environment probe.** In EVERY session, once `references/policy.md` has been read (next paragraph; the `Environment` table lives there), compare the operating-system-and-shell cell of the `Environment` table with the actual one; on a mismatch, or when the user says the setup changed, re-probe (show the diff; the user confirms). If the SHA-256 tool or the real-path tool is missing, report it to the user and stop skill resolution (Gate 2 step 3d); never invent a method. On the first run on a machine, when the `Environment` table of `references/policy.md` is missing, or when the user says the setup changed, probe each item of that table read-only (operating system and shell, tool for the SHA-256 of a file, tool for a real path, how to close standard input, how to start a background process, terminal multiplexer yes or no, scripting runtime for parsing JSON yes or no, how to wait a short interval, how to read the current time). Show the user the diff, and write the table only after the user confirms. Never install anything: a missing tool is reported to the user, who decides. Any tool that gives the same result may be used and is recorded in the table with its date.

Read `references/policy.md` first, then do the Environment comparison above. If it is missing, or the user says the setup changed, ask the user for each item in it, write the answers there, and show the diff before saving. Nothing in these rules overrides the policy, and nothing in the policy overrides the hard rules above. Compare the policy's "Orchestrator" item with the agent session that is actually running this skill; if they differ, ask the user which is right, and update the policy (diff first).

### Gate 1A: Re-check the CLIs recorded in the table

Run these checks for the CLIs that the table names (read-only, no user question needed). For each CLI use the checks recorded for it in the models table and in the section `Pre-flight check commands` of `references/models-and-commands.md`; a CLI with no recorded check is treated as unverified (Gate 1B).

1. Login check. A CLI named in the table that is missing, or not logged in, on this machine is reported to the user and is not used. If the CLI has no login-status command, a successful query is the evidence, and say that this is an inference.
2. Live model list. Compare it with the models table in `references/models-and-commands.md` and update the table if they differ (see "Keeping this table current" and "How to write into the table" there). Parse a long machine-readable list; never print it whole.
3. Effort must be valid for the model, as recorded in the models table (for example, some models have a fixed effort and reject an effort flag).
4. Run in the intended working directory, not a temp directory, when the user wants to see the session later.
5. Quota read: read the quota percentage if a way exists (record in the table whether one was found).
6. Session-list command: check that the one recorded for each CLI in the table still works (it runs and lists sessions). A CLI whose recorded list command no longer works is reported to the user and is not used.

Report the result in one short block. A subagent of the host's own mechanism needs no CLI check, but it must still be a row in the table. Its row counts as session-list verified once the user has confirmed, one time, how the host shows the runs of its subagents; record the confirmation and the way to see them, with the date, in the Session-list table of `references/models-and-commands.md`. Until then such rows are not chosen.

### Gate 1B: Any other CLI the user listed

Used when the user adds a list to the flag (example: `/diff-type-subagents I installed: <CLI one>, <CLI two>`), or when the table was missing or empty and the user named the installed CLIs. Do not reuse the models table for any CLI on the list. Treat every one as unverified and go through these steps in order, per CLI:

1. **Check auth.** Find that CLI's own way to show login status. If it has none, use a successful query (for example listing its models) as the evidence, and say that this is an inference. Do not assume it is logged in.
2. **Ask the user whether to spawn a "Hello" test task**, and state the purpose in the question: to confirm that the CLI is logged in, that its non-interactive command works, and that the session is saved and visible in that CLI's `/resume`. Say also that the test includes five small read-only capability checks (step 3b). Do not spawn the test before the user agrees. If the user declines, do not use that CLI as a subagent until it has been verified, unless the user explicitly says to skip verification.
3. **If the user agrees, run the test.** Run an interactive session in the intended working directory, in the safest mode (read-only, no dangerous or bypass flags), send `Hello`, and exit cleanly. Use a terminal multiplexer for this only if the `Environment` table of `references/policy.md` says one exists; otherwise use the CLI's non-interactive command for the test, or ask the user to run the interactive session in their own terminal and report what they see. Never install a multiplexer. Give the user the exact input, the exact output and the session ID, so the user can compare them with what that CLI's `/resume` shows. Wait for the user to confirm that the session is visible and matches. Also find, from the CLI's own help or official documentation, the exact command that lists every worker session of that CLI, including non-interactive sessions and sessions started in another directory, and test it. Check whether a session that is still running can be opened and followed in real time.
3b. **Probe the capabilities (read-only, covered by the consent in step 2).** If the CLI has no read-only mode for these prompts, say so and ask the user before testing; never use a bypass flag. In the intended working directory, send five tiny read-only prompts and one write check, one per column of the `Worker capabilities (per CLI)` table: (a) = `Reads path`: read a file by absolute path inside the working folder that holds a known token; (b) = `Reads outside folder`: read a file by absolute path OUTSIDE the working folder, a scratch file created for the probe under the operating system's temporary folder (never in a tracked folder), holding a different token, and deleted after the probe; (c) = `Runs commands`: run a harmless command that prints a fixed string (and, if the tasks need tests, a no-op test command); (d) = `Web`: the orchestrator first opens an official documentation page of the CLI's own vendor and notes its exact title, then asks the worker for that page's title; (e) = `Sees skills itself`: ask the worker to list the skills it can see, and where from; (f) = `Writes files`: ask the worker to create ONE throwaway file in its own task folder and read it back (no existing file is touched), once per mode the CLI offers that is not a bypass; the read-only wording of the other checks stays.
   Pass rules: (a) and (b) are `yes` only if the reply is exactly the known token of that file; (f) is `yes` only if the file exists with the expected content when the orchestrator reads it, and the orchestrator then deletes it; (c) is `yes` only if the reply is exactly the fixed string the command printed; (d) is `yes` only if the worker's title matches exactly; (e) is `yes` if the worker lists at least one skill or rule file with its folder and the orchestrator confirms that file exists, `no` if it replies that it sees none, and `[Unverified]` if the answer cannot be matched to an existing file. Anything else is `[Unverified]`; a cell is `no` only when the reply clearly shows the action is not possible. Each cell carries the check date and names the sandbox or permission mode used for the check, because a read-only mode can block an action that the CLI can do in another mode. A check that was not run stays `[Unverified]` and is never assumed.
   **Eligibility.** A task needs a column when its brief requires that action (a file by absolute path, a file outside the working folder, a command such as a test run, a web page, a skill the worker must find itself, or to create or edit a file in its own folder or allowed paths: column `Writes files`). The orchestrator lists the needed columns for each task in `assignments.md` and checks them against the table at Gate 2. A worker whose cell is `no` or `[Unverified]` in a needed column is not eligible for that task. The six cells are recorded at step 6, in the `Worker capabilities (per CLI)` table.
4. **After the user confirms, list that CLI's models and effort levels** from the CLI's own commands or official documentation: the models, the minimum and maximum effort, which models have a fixed or non-adjustable effort, and whether quota or usage can be read. Say which facts are verified and which are not.
5. **Only then may that CLI's agents be used as subagents.** Add a new CLI to the fallback order in the policy and to a task's assignment only by the user's decision: propose a place for it and ask, never invent its position.
6. **Record what was discovered. This step is mandatory.** Before the CLI's agents are used for real work, add a row for every discovered model to the models table in `references/models-and-commands.md` (vendor and CLI version, model id, effort levels, notes such as "effort fixed" or "not adjustable"), record the CLI's session-list command and whether a running session can be followed in real time, and update the commands, pre-flight checks and quota notes if this CLI differs from the CLIs already in the table. Also add one row per CLI, with the five cells and the check date, to the `Worker capabilities (per CLI)` table in the same file. Mark anything not verified as **[Unverified]**, and write the date. Tell the user which rows were added. Do not leave discovered models only in the conversation. Show the user the diff before writing it as final, and commit only when the user allows it.
7. **Probe the skill folders (read-only; also run for the orchestrator itself).** Find where this agent looks for skills and whether it scans a folder by itself: its documentation, its help, the folders that exist on this machine. Change nothing. Show the findings to the user; write them to the "Skill source roots" section of `references/policy.md` (with the date, and [Unverified] for what was not tested) only after the user confirms. For the orchestrator, ask the host first, then the user.

A subagent of the host's own mechanism, and the orchestrator rules, do not depend on any CLI. They are available whenever the host has them.

### Gate 2: Delegation plan and approval (before the first delegation, and whenever anything changes)

1. Before the first delegation, create `<handoff-root>/YYYY-MM-DD-<topic>/assignments.md`. The file starts with two lines, `Status: draft` and `Next step: <the next action; the questions waiting for the user>`. Step 4 and step 6 change the first line; the orchestrator rewrites the second after every launch, result, question and answer, and writes every allocation decision and every user decision to a file when it is made. A table with no `Status` line is `draft`: add the line. Besides the main table, the file holds the sections `Skill resolution`, `Delivery table`, `Parallel groups` and `Allocation record`. Under the two lines, one row per task: `work item | worker | model | effort | read-only or write | allowed paths (plan files + ripple list) | ripple classes | CLI verified | skills the worker must read | why | needed capability columns | escalation chain | time limit | parallel group`. The `escalation chain` column names the next rows in advance; the choice and the chains are also written to the section `Allocation record` of `assignments.md` (`references/allocation.md`). `<handoff-root>` is the handoff folder from `references/policy.md`; it must be ignored by git. For each task, "skills the worker must read" lists every skill that applies to that task: the skills the user selected for the workflow step this task belongs to (a selection file of a workflow is optional input: when the user keeps one, use it; without one, the orchestrator's own judgment of what applies decides), plus any other skill the orchestrator judges relevant to the code or files the task touches (for example a language or framework skill, a testing skill, a UI skill). Write "none" only when no skill applies, and say why. The user can add or remove skills when confirming the table. The table always ends with a row "R" for the final whole-branch review (Gate 6 step 1a): it says which review mechanism the orchestrator will use, and asks the user whether to add an independent read-only reviewer worker (with its model, effort and the review skill it must read).
2. Assign only a CLI and model that passed Gate 1A or Gate 1B and appear in the models table. A subagent of the host's own mechanism needs no CLI check but must be a row in the table, and is chosen only after the user has confirmed how the host shows its subagent runs (Gate 1A). Show the user, per chosen row, what is [Unverified] about its session list (other folders, following a live run).
3. Choose workers by `references/allocation.md` (steps 0 to 8): weigh each task, filter the rows, rank by tier only (never by price), spread equal choices as the policy says, write the choice and the escalation chain into the `Allocation record`. A row with no recorded result for a kind of task may be chosen as a pilot, with a closer review. If a step leaves no row, stop and ask the user; never downgrade silently.
3a. **Ripple scan (before the table is shown).** For every task that writes, find what its change will break elsewhere BEFORE the allowed paths are fixed. Use read-only means only (search, the compiler or type checker's view, the project's schema and contract tools, reading the guard checks). The orchestrator performs the scan itself, read-only; it is never delegated before approval. List, per task:
   - **Consumers** of whatever the task changes: code that calls, imports, queries or builds it (a type, a function, a table or column, an endpoint, a message or event, a config key, a public contract), plus generated artifacts derived from it (clients, ORM models, schema files, API docs).
   - **Tests, fixtures and seed or sample data** whose assertions or values describe the behavior the task changes on purpose.
   - **Guard checks** that cover the touched area (type check, lint, architecture or boundary rules, schema or migration validation, contract tests, translation key checks) and what they require.
   - **Ordering and compatibility:** whether the change makes a check red, or breaks a running consumer, between this task and a later one (a new required field, a removed export or column, a migration that a deployed version does not yet understand). Reorder the tasks, or split the change in compatible steps, so every commit stays green and, where it matters, every step is safe to deploy.
   The result is the task's ripple list. Allowed paths = the files the plan names + the ripple list.
3b. **Pre-approved ripple classes (the user chooses them when confirming the table).** A class is a kind of mechanical edit a worker may make without stopping, only in files of the ripple list:
   - propagate a change to the places the compiler, type checker or schema validator flags (for example a new field or parameter, a renamed column in queries);
   - update an existing test or fixture so it asserts the behavior this task changes on purpose (never delete, skip or weaken it);
   - regenerate a generated artifact with the project's own command;
   - satisfy a guard rule the project already enforces (public entry point, declared key list, naming).
   The brief's "Allowed paths" section names each class and the exact files it covers, so WORKER RULES item 2 stays word for word true. The worker reports these edits under a heading "Ripple edits", and the orchestrator reviews them like any other change. An edit outside the classes, or in a file that is not in the list, is a stop (CODE WORKER RULES item 4 applies unchanged).
3b-bis. **Never a ripple class; always a stop and a question to the user:** anything irreversible or destructive or touching real data (dropping or rewriting data, editing a migration that has already shipped or run, a data backfill, changing a contract consumed outside the repository, deleting a resource, touching production or a user's live database). For these the orchestrator also shows the plan first and asks for a backup or a dry run before anything is carried out.
3c. A small correction of the same task may resume the same worker session instead of opening a new one.
3d. **Resolve skills.** For each skill name in "skills the worker must read", follow `references/skill-delivery.md` section 1: walk the roots of `references/policy.md` in order, take the real path, compute the combined hash, and write one row into the section `Skill resolution` of `assignments.md` (`skill | real path | root | combined hash | covered files | note`). A conflict, a missing skill, a broken link, a missing linked file or a policy without roots is a stop: ask the user, never guess. If the machine has no SHA-256 tool or no real-path tool (see the `Environment` table of `references/policy.md`), report it to the user and stop skill resolution; never invent a method.
3e. **Choose delivery modes.** The delivery mode is evaluated per CANDIDATE row inside allocation step 2 (`references/allocation.md`): a row needs at least one working mode for every skill of the task. Follow `references/skill-delivery.md` section 2: take the first mode that the row's capability cells allow (`path`, `workspace-copy`, `compiled`, `orchestrator-keeps`). The final `Delivery table` of `assignments.md` (`worker | skill | mode | proof | confidence`; proof and confidence from section 3) is written after the row is chosen (and after any split). At approval it lists a row for every (worker, skill) of the chosen rows AND of every row of their escalation chains (a chain row already passes allocation step 2, so a working mode exists for each skill). If no mode works for any row, stop and ask the user: change the worker, or allow the work without that skill.
3f. **Parallel groups.** Evaluate the whole task list for which tasks may run at the same time, by `references/parallel-groups.md`: conflict edges (the file is the unit), groups `G1`, `G2` and so on, the split evaluation (a split is only proposed, never applied silently), the `Parallel limit` of `references/policy.md`. Write the `parallel group` column and the section `Parallel groups` of `assignments.md`. Parallelism does not depend on the vendor. Order of Gate 2 step 3 and its sub-steps: the ripple scan (3a), the ripple classes (3b), the skill resolution (3d), the parallel groups and any split (3f), then the allocation of step 3 run group by group in order (the delivery mode of 3e is evaluated per candidate row inside its step 2), then the `Delivery table` (3e) for the chosen rows and their chain rows, then the table (step 4).
4. Show the table, with the `Delivery table` and the `Parallel groups` section, to the user and **stop until the user confirms all of them**. Confirming the table also confirms the ripple lists and the ripple classes in it. Only then change the first line to `Status: approved`, together with a dated line that quotes the user's confirmation (this is also what Gate 3 requires before any delegation). A summary, a ledger or a remark that the user "seemed fine" never makes a table approved. With `Status: draft`, or with no status line, nothing is delegated. A run launched before approval is a violation: tell the user, keep its result only as a lead (in `notes.md`, under the heading "Leads (run before approval)"), and show the table again for confirmation.
5. Ask step 5 (working folders) BEFORE showing the table of step 4 for approval; if the answer changes a group (edge (f)), re-evaluate the groups before the table is shown. If any worker needs write access, ask the user whether it writes on the current branch or in an isolated worktree. Never assume. Writers that run at the same time need separate worktrees (each its own working folder) or clones that the user allowed; a branch alone does not give a second working folder. The working folder of every concurrent run, including the copy of the committed state given to a read-only run, is named in the approval table, in the cell of the column `allowed paths (plan files + ripple list)` of that run's row, as a line `working folder: <path>`.
6. Any change of worker, model, effort, write permission, scope, delivery mode or skill hash (Gate 4 step 2a re-check, the failure rule of `references/skill-delivery.md`) updates `assignments.md`, sets `Status: draft` at once, and needs the user's approval again before it is carried out. The one exception is a move along the escalation chain the user already approved with the table (every chain row already has its Delivery table rows at approval, so a move along the chain needs no new row and does not reset `Status`): it needs no new approval, but it is told to the user and recorded.
7. Do not delegate just because a task is simple or a worker is available.

### Gate 3: Delegation check before every step of the workflow in use

Before each step of the workflow in use (for example, with Superpowers: brainstorming, research, spec, plan, implementation, verification, review), answer in one line: "Delegable? yes/no, worker or reason". Default is **yes** for research, codebase reconnaissance, builder checks, plan-task code and independent review; **no** for talking to the user, approval gates, git commits, merges and pushes. If the answer is yes and the step has no row in `assignments.md`, go back to Gate 2 and get approval first. Nothing is delegated before approval: delegation needs `Status: approved` in `assignments.md`.

### Gate 4: Brief and handoff (every delegated run)

**Before creating any brief, read `references/worker-rules.md`.**

1. The orchestrator creates the task folder under `<handoff-root>` (from `references/policy.md`, ignored by git):
   ```
   <handoff-root>/YYYY-MM-DD-<topic>/<task-id>/
   ├── brief.md          goal, scope, allowed paths, output format, stop condition
   ├── ledger.json       one entry per run, marked pending, running, done, or failed, with the agent and model that ran it
   ├── notes.md          sources found, items still unsure, decisions taken
   └── results/
       └── batch-NN.json one result file per batch, written as soon as the batch finishes
   ```
   A RUN is one ledger entry; a BATCH is a result file `results/batch-NN.json` inside a run. A single read-only run needs only `brief.md`, its run entry in `ledger.json` and its log or result; `notes.md` and `results/` are for runs with several batches or for write tasks.
2. `brief.md` starts with the WORKER RULES block from `references/worker-rules.md`, copied word for word, for every worker. For a worker that writes code, the CODE WORKER RULES block follows it, also word for word, then the plan task's own steps (they carry the exact test names, signatures and commands). Then the task, its allowed paths, its output file and its stop condition. For a read-only task with no output file, the task part says that the answer is the worker's final reply and that the orchestrator saves it. Never write "follow the project rule file" or "use the skill" in a brief; deliver each skill by its mode as step 2a says. The command prefix of `references/policy.md` applies to commands the orchestrator runs and reads; it is never part of a command given to a worker or run through the launch wrapper (its output goes to a log file).
2a. **Skills for the worker (every worker, whether of the same vendor as the orchestrator or another).** A worker does not see skills, so for every skill listed for this task in `assignments.md`, deliver it by the mode in the `Delivery table` (`references/skill-delivery.md` sections 2 to 4). Recompute the combined hash of the skill right before the brief is written and stop if it changed (section 1). Name every skill that applies, one entry each; never a name only, and never a summary in place of the path, the copy or the checklist.
   - `path`: the brief names the real path with the sentence of section 2.
   - `workspace-copy`: the brief names the copy's path; it never states the nonce.
   - `compiled`: the checklist of section 4 is in the brief, nonce on its first line.
   - `orchestrator-keeps`: the skill is not in the brief.
   - Record in the table `Worker capabilities (per CLI)` whether the CLI can read a file by path; a nonce is fresh per worker, per skill and per run, and is written to `ledger.json` (section 2).
3. **Where a worker may write:**
   - A code worker may modify the source files listed under the user-approved "Allowed paths", and only those.
   - Reports and results go only to the output path named in the brief. A read-only worker's result goes back to the orchestrator (either the CLI's own option to write its last message to a file, as recorded in the models file, or a redirection of the CLI's output, in both cases into a file inside the task folder).
   - "Inside its own task folder" applies to state and result files (`ledger.json`, `notes.md`, `results/`), which the orchestrator writes. It never blocks a code worker from editing its allowed source paths.
4. **One task, one fresh session.** Do not carry one chat from task A to task B: no anchoring on earlier conclusions, the rules sit at the top of a short context, a short context uses less quota, and each task may use a different model and effort. Reusing a session is allowed only for a retry or a small correction of the same task while the context is still small. The files stay the source of truth.
5. **Keep workers on task:** one output file with a fixed schema; list the paths a worker may read and write, a stop condition, and "do nothing outside this list"; run non-interactive so workers cannot ask questions back (stdin closed, see `references/running-workers.md`); small batches that finish quickly, with results written to disk after every batch; constrain prompts tightly, because some models add follow-up work on their own.
6. Deliverables that the user reviews or that belong in the project (reports, specs, plans) go to the tracked location the task's spec or plan names, built from the `results/` files. A task folder that lies under a path ignored by git (by any `.gitignore` in the project) needs no cleanup: leave it in place and do not ask about it; delete it only if the user asks. If a task folder is NOT ignored by git, tell the user that it is not ignored (so it would show in `git status` and could be committed by mistake), never commit it, and let the user choose: add its path to a `.gitignore`, move it to an ignored path, or delete it.
7. **Launch so that the chat is not blocked.** Start every run as its own process (or the host's background subagent) as described in `references/running-workers.md`: the launch wrapper, a ledger entry with the baseline of the working folder (Gate 5) recorded before the launch call and marked `running` with the launch time right after it returns, the `done` marker, the time limit and the rule for parallel runs. The tasks of one group (`references/parallel-groups.md`) start together, unless the parallel limit forces them to start in parts; write members only in separate worktrees (each its own working folder) or clones that the user allowed, otherwise one after another in group order; record each concurrent writer's working folder in its ledger entry; a later group starts when the tasks it depends on are done and reviewed. Never run a worker as a blocking command in the chat. A run is finished only when its `done` marker exists.
8. **Session check after every launch.** Right after starting a worker, run that CLI's session-list command from the models table and confirm that the new session is listed. Give the user the session name or ID and the exact command to open it. If the session is not listed, pause that run (do not continue the task with it), tell the user exactly what you saw, stop the process only after the user agrees, and let the user decide what to do (for example another run mode, or another CLI). Do not continue the task with an unlisted session.

### Gate 5: Compliance check after every worker run (mandatory, by the orchestrator)

A run is finished when its `done` marker exists (`references/running-workers.md`). Read `exit.code`: absent or not 0 means the run failed (Gate 6 step 2). Never read a run's result before `done`. The check is made per run against that run's allowed paths. Record its result as `compliance` (`passed` or `failed`) in the run's ledger entry.

BEFORE the launch call the orchestrator records, in the run's ledger entry, a baseline of the working folder the run uses: the `git status --porcelain` output, the head hash, a fingerprint of the tracked changes and the list of untracked files. The result needed: any change since launch is detectable, including a change to a file that was already modified and any untracked file (example only: a hash of `git diff` for the fingerprint, and `git ls-files --others --exclude-standard` for the list). The check compares the run's own working folder with that baseline: the commit count and head hash unchanged, and `git diff --name-only` inside the allowed paths (add the command prefix from the policy, if any). A read-only run must show NO change at all (there is no allowed-path comparison to make). Two runs must not share one working folder if either writes: a read-only run that is active at the same time as a write run has its own working folder (a separate worktree or a copy of the committed state) or, if it cannot, is placed in a later group (edge (f) of `references/parallel-groups.md`). On any violation: stop, show the user exactly what happened, undo only what the worker changed outside its allowed paths after the user agrees, and do not treat that run's output as valid. A worker's own statement that it followed the rules is never evidence.

**Skill-read check (same gate, every run).** For every skill named in the brief (step 2a), check the proof of its mode (`references/skill-delivery.md` section 3) and give the result its confidence label:
- `path`: the worker's log shows an open event for the skill file (section 3) before the first step of the work. Confidence high. A `path` run whose log cannot show the order of events is not allowed: the mode is `workspace-copy` from Gate 2.
- `workspace-copy`: the nonce line of the copy is quoted in the report. Confidence medium.
- `compiled`: evidence for every step, the nonce quoted, and the orchestrator re-ran the verification commands and they agree. Confidence lower.
- `orchestrator-keeps`: verified by whoever holds the work; the label is that of the holder's own mode.
A result from `workspace-copy` or `compiled` gets a closer review, like a fallback to a weaker model. Failures (each makes the run invalid; stop and tell the user which skill): `path` with no open event: mark `Reads path` [Unverified] in the capability table (show the diff first), take the next mode. `workspace-copy` with a missing nonce: mark `Reads path` [Unverified], take `compiled`. `compiled` with a step lacking evidence, a missing nonce, or a re-run that disagrees: take `orchestrator-keeps`. In every case ask the user to approve the changed `Delivery table` before the run is repeated. If `orchestrator-keeps` cannot be verified by its holder, or no mode works: stop and ask the user (change the worker, or allow the work without that skill). A worker's statement that it followed a skill is never evidence.

### Gate 6: Review, quota, fallback and recovery

1. **Review.** Read the diff, run the verification commands yourself and read their output. For every disputed item and for a sample of "verified" ones, read the newest official page yourself. Review every task and the whole branch. Record the result as `review` in the run's entry of `ledger.json`. This reading is the first step of review, never the whole of it: step 1a adds the final review.
1a. **Final review, when every task is done and before the branch is offered for merge (mandatory).** Reading the diff yourself does not replace it. Run both of these, in this order, and record each result in the ledger:
   - **The orchestrator's own review mechanism on the whole branch.** Use the review capability the orchestrator's host provides (for example a code-review skill or command, or a requesting-code-review skill), at the effort level the user allows and never above the policy's effort ceiling. Choose the effort from the size and risk of the diff being reviewed: **low** for a small mechanical or documentation-only diff; **medium** for a small diff that changes logic; **high** for a large diff, or one that touches scoring, persistence, migrations, security or a public contract. A final whole-branch review is sized by the whole branch, not by the last commit. Record the level and the reason in the ledger. Name which mechanism was used. If the host has none, say so, and the independent reviewer below becomes mandatory.
   - **An independent reviewer when the user wants one (row "R" of `assignments.md`).** A read-only worker, in a fresh session, that is not the session that wrote the code, chosen by `references/allocation.md` (step 3): its family must differ from the family of the writer of the highest-risk task, with the same relaxation and label `low` independence if no such row exists. It follows Gate 4 and Gate 5 like any worker: a brief that starts with WORKER RULES, the review skill or method delivered by its mode (Gate 4 step 2a), with its proof checked (Gate 5), the diff range to review, and a single output. Its findings are leads: verify each one yourself before acting, re-grade by effect, fix Critical and Important findings with a failing test first (through a worker, under Gates 2 to 5), and record Minor findings as deferred.
   Do not tell the user that the work is reviewed until both applicable steps are recorded. If the user chose "orchestrator reviews, no independent reviewer", record that choice and still run the orchestrator's own review mechanism.
2. **When a worker stops** (quota, error, timeout) or is stuck (`references/running-workers.md`, Hang detection): read the ledger, check the last "done" batch for truncation, then give the successor the brief, the finished results and the notes with the instruction "continue from the first batch that is not done; do not redo done batches". A batch that was being written when the old agent stopped counts as not done and is redone. The orchestrator does not take the task over itself and does not restart it from zero.
3. **Fallback goes through files.** The new agent never receives the old agent's session. Build a new brief from the files, never by retelling from memory. `notes.md` must record sources found, items still unsure and conventions agreed, because the old agent's private reasoning is lost.
4. **Quota and fallback:** a fallback follows the escalation chain approved in `assignments.md` (`references/allocation.md`); the fallback order, the equivalents and the quota thresholds are in `references/policy.md`, and never lower a task's tier silently. After the last entry in the fallback order is exhausted: stop, save the ledger, report the state to the user, and do not continue. A result produced after a fallback to a weaker model gets a lower confidence label and a more careful review. For high-value work where accuracy matters, tell the user that waiting for the quota to reset may be better than a weaker model, and let the user choose. Detect running out of quota reactively: a non-zero exit code, a rate-limit or usage-limit message in the output, or HTTP 429. Tell the user each time a fallback happens: which agent, which task, which batch, and why.
5. **When the orchestrator itself stops** (quota, error, closed session): all state is in the task folder (`brief.md`, `ledger.json`, `notes.md`, `results/`) and in `assignments.md` at the topic level (its `Status:` and `Next step:` lines). A new orchestrator session, started by the user with an agent the user chooses, reads those files and the assignments, runs Gate 1, and continues from the first obligation (run, compliance, review) that is not passed. The user decides which agent takes over (a new session started by the user is the user's choice of successor); the orchestrator never appoints its own successor. The new session starts with step 6.
6. **Resume point.** After a context compaction, when a session is reopened, or whenever the orchestrator cannot tell what was decided, it first re-reads `SKILL.md`, `references/policy.md` and `assignments.md` (and the references the situation needs) before it delegates or reviews anything. It reads `assignments.md` FIRST (the `Status` and `Next step` lines), then every per-task `ledger.json` of the topic, and starts from the first obligation (run, compliance, review) of any run that is not passed; `status: done` means only that the process finished. If `assignments.md` is absent or its `Next step` is stale, ask the user; never assume. Every allocation decision and every user decision is written to a file when it is made, never kept only in the conversation; a decision found only in a summary or in memory is asked again. `assignments.md` is approved only by its `Status: approved` line with the dated quotation (Gate 2 step 4). A run launched before approval is kept only as a lead in `notes.md` under "Leads (run before approval)".

## Red flags

| Thought | Reality |
|---------|---------|
| "I'll just do this one myself, it's quick" | Run Gate 3. The default for delegable work is to delegate. |
| "The task is simple, I'll delegate without the table" | Nothing is delegated before the user approves `assignments.md` (Gate 2). |
| "The user already approved the plan, so the assignment is approved" | Approval of a spec or plan is not approval of the assignment. |
| "I'll switch the model, it's a small change" | Any change of worker, model, effort, write permission or scope needs approval again (Gate 2 step 6). The one exception is a move along the escalation chain approved with the table. |
| "I'll tell the worker to follow the project rule file" | It cannot see it. Read `references/worker-rules.md` and put the blocks in `brief.md`. |
| "The plan steps are enough, the worker doesn't need the skills" | A worker sees no skill. If a skill applies, deliver it by its mode (Gate 4 step 2a) and check its proof (Gate 5). |
| "The skills the user selected for this step are for me, not for the workers" | They apply to whoever does the step's tasks. Put them in the assignments table and in each brief. |
| "A worker of my own vendor surely has the skills too" | Never assume. A same-vendor worker is a fresh session with no skills until its brief names them. |
| "This CLI surely reads files outside its folder" | Never assume a capability. Probe it at Gate 1B (step 3b); an unprobed cell is [Unverified] and the worker is not eligible for a task that needs it. |
| "It cannot read the path, so skip the skill" | Choose the next delivery mode (`workspace-copy`, `compiled`, `orchestrator-keeps`) from the probe. If none works, ask the user; never drop the skill silently (`references/skill-delivery.md` section 2). |
| "It quoted the skill, so it read it" | A worker's statement is never proof. Check the proof of the mode: an open event in the log, or the fresh nonce and per-step evidence (section 3). |
| "I know where this skill lives" | Paths come from the `Skill resolution` table, never from memory or from where a skill was loaded (Gate 2). |
| "The skill is the same in both folders" | Compare the combined hashes. Different hashes are a stop, not "first root wins". |
| "The worker ran fine, its session list doesn't matter" | Every worker session must be listed and checkable by the user. Run the session check (Gate 4, step 8). |
| "I'll write this model or vendor name into the rules" | Machine and user settings live only in `references/policy.md`. The rules stay vendor-neutral. |
| "The worker said it passed" | Run the command yourself (Gate 6). |
| "I read the whole diff and the tests are green, so the branch is reviewed" | That is step 1 only. Run the final review (Gate 6 step 1a): the host's own review mechanism, and an independent reviewer if the user wants one. |
| "The user chose 'orchestrator reviews', so no review tool is needed" | The choice removes the independent reviewer, not the host's review mechanism. Run it and record it. |
| "Any CLI named in a request is surely installed" | Never assume. Table has rows: re-check it (Gate 1A). No table: ask the user, then discover (Gate 1B). |
| "The table lists this model, no need to check the machine" | Re-check the live CLI against the table every session (Gate 1A). |
| "This listed CLI is probably logged in" | Unverified until Gate 1B is done. |
| "I found a new model, I'll remember it" | Write it into the models table, or the next session loses it. |
| "I'll just pick the cheapest model" | Rank by tier only, never by price (`references/allocation.md` step 5). Cost is quota, not price per token. |
| "Everything goes to one family, it is simpler" | Apply the Spread setting at step 6 of `references/allocation.md`; if only one family passes step 2, say so to the user. |
| "Task A and task B can share one chat" | One task, one fresh session. State goes through files. |
| "It should be done by now" | Check the `done` marker, then the limit counted from the launch time in the ledger entry. Past the limit with no `done`: Hang detection. |
| "The notification will come, I do not need the marker" | Files are the source of truth. Never report a result before its `done` marker exists; under `polling` check at every pause point. |
| "My summary says the user approved it" | A summary is not approval. Only `Status: approved` with a dated quotation of the user's confirmation in `assignments.md` counts (Gate 2 step 4). |
| "I remember the decision" | After a compaction or in a new session, re-read the files first (Gate 6 step 6). A decision that is not in a file is asked again. |
| "There is no selection file, so no skill applies" | A selection file is optional input. Without one, judge what applies to the task yourself (Gate 2 step 1). |
| "These tasks look independent, I will start them all" | Independence is decided by the conflict edges, with the file as the unit, and by the `Parallel limit` (`references/parallel-groups.md`). Two tasks that edit different parts of one file still conflict. |
| "They are different vendors, so they run one after the other" (or "...so they may overlap") | Parallelism does not depend on the vendor. Only the edges, the group rule and the limit decide, and write tasks at the same time need a worktree the user allowed. |
| "The worker is stuck, I'll finish it myself" | Hand the files to a fallback agent: continue from the first obligation (run, compliance, review) that is not passed; inside a run, from the first batch that is not done. |

## Reference files

- `references/policy.md`: machine and user settings (orchestrator, forbidden models, effort ceiling, fallback order, equivalents, quota thresholds, command prefix, handoff folder). Read at Gate 1.
- `references/models-and-commands.md`: models table and how to keep it current, worker capabilities, command shapes, session visibility.
- `references/allocation.md`: how to weigh a task and choose its worker (steps 0 to 8), the roles and families, the escalation chain and the `Allocation record` table. Read at Gate 2 step 3.
- `references/skill-delivery.md`: how a skill name is resolved to a real path and a combined hash (section 1), how it is delivered to a worker by mode (section 2), how reading is proved (section 3) and the compiled checklist format (section 4).
- `references/running-workers.md`: how a worker runs as its own process: the launch wrapper, the `done` completion marker, the completion signal (`native` or `polling`), hang detection and the time limit, and parallel runs. Read at Gate 4.
- `references/parallel-groups.md`: how a task list is evaluated for parallel groups: inputs, conflict edges, the group rule, the split evaluation, limits and the record in `assignments.md`. Read at Gate 2 step 3f.
- `references/worker-rules.md`: the WORKER RULES and CODE WORKER RULES blocks, to copy word for word into briefs.
